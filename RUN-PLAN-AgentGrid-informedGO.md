## 0. Субъект

**Agent Grid: управление статусом + Logout.** Requirement-driven (чище по изоляции, чем AI-виджет) →
выбран как **первый прогон**. Logout — **реальная команда на CC-платформу (Finesse)**, не «UI + строка в БД».

## 1. Гипотеза прогона (из E-022 §1)

Опросник, сгенерированный аппаратом по легибельным артефактам (спека / CLAUDE.md / git / код), захватит
достаточно тацитной модели автора, чтобы **квалифицированный не-автор** провёл изменение «status+Logout»
без тихого слома инвариантов — на качестве автора, меряемом **исходом**.

## 2. Killer-поверхность опросника (5 инвариантов) — В ЗАПЕЧАТАННОМ КОНВЕРТЕ

> **Критично по целостности:** эти 5 пунктов координатор перечислил при планировании — но в прогоне
> они идут **только** в пред-регистрацию автора (§3) и **карантинятся** от аппарата и оператора.
> Аппарат обязан их **переоткрыть** из артефактов или не задать — и это переоткрытие/непокрытие мы и
> меряем (поверхность **A**). Если влить список в опросник — тест мёртв.

| # | Инвариант | Где живёт / почему тацитный | Как детектить тихий слом (исход) |
|---|---|---|---|
| I1 | **CC-propagation**: logout = реальная команда Finesse, не UI+БД | «очевидно автору», редко в спеке | после logout проверить **состояние агента на платформе**, не строку БД |
| I2 | **Authz по скоупу супервайзера [PG-04]** | правило есть, его применимость к logout — тацит | действие через границу скоупа → должно быть **отказано** |
| I3 | **Audit: Agent.LoggedOut / StatusChanged** | новые события, нигде ещё не описаны | после действия — события в audit-логе, корректные |
| I4 | **Staleness (указатель E-005)** | окно свежести статуса | отображаемый статус не устаревает за пределы окна |
| I5 | **Status Group / ISO-KPI defs** | как статусы сворачиваются в KPI | смена статуса корректно мапится в группу/KPI, без перекоса |

## 3. Пред-регистрация автора (шаблон — ЗАПЕЧАТАТЬ до §4)

Автор заполняет и **запечатывает** (не видно аппарату и оператору до §6):

1. **Change-spec:** что именно делаем в Agent Grid (status management + Logout), границы изменения.
2. **Авторские решения и trade-offs:** как Я бы спроектировал (пер-инвариант: I1..I5 + прочее).
3. **Трогаемые инварианты:** I1..I5 (§2) + любые ещё, которые автор держит в голове, но не записал.
4. **Ожидаемые verification-артефакты:** что проверять и чем (платформенное состояние, authz-кейсы,
   audit-лог, staleness-окно, KPI-маппинг).
5. **Контаминация-обязательство:** автор НЕ коучит в §4–§6; любое его вмешательство логируется.

## 4. Генерация опросника аппаратом — БЕЗ автора

- **Вход разрешён:** спека / CLAUDE.md / git-история / код / wireframes — всё **легибельное**.
- **Вход запрещён:** голова автора, запечатанный конверт (§3), список §2, прямой коучинг.
- **Задача аппарата:** выявить точки решения для «status+Logout» и сгенерировать опросник.
- **Инструментовка (для классификации A/B):** зафиксировать, **какие из I1..I5 опросник поднял**,
  какие — нет. Непокрытый инвариант = кандидат на поверхность **A** (неполнота опросника).

## 5. Оператор-не-автор — fork-1: АГЕНТ первым

- **Кто:** холодная агент-сессия **без** контекста этого обсуждения, без конверта §3, без списка §2.
  Опирается **только** на опросник + легибельные артефакты.
- **Действие:** отвечает на опросник и ведёт изменение до verification-gate.
- **Лог:** где колебался; **где обратился к автору** (сигнал неполноты/контаминации).
- **Второй якорь (позже):** реальный квалифицированный человек-не-автор — для прямой заявки #1.

## 6. Verification-gate и критерии исхода

- **Gate (E-002):** артефакт против истины; затем конверт §3 **распечатывается** и прогоняются
  детекторы I1..I5 (§2, колонка «как детектить»).
- **ЗАРАБОТАЕТ:** gate пройден И **ни один** из I1..I5 не сломан тихо; расхождения с автором —
  нейтральны/улучшения.
- **ОСЛАБИТ/УБЬЁТ:** тихий слом инварианта, **который опросник не спросил** (поверхность **A**,
  «незаданный вопрос») ИЛИ корректный ответ потребовал авторской модели (**инверсия компрессии**).
- **Классификация каждого промаха:** **A** (опросник не спросил) vs **B** (спросил, оператор ответил
  неверно). A → чинить элиситацию; B → слой валидации ответов.

## 7. Метрики (исход, не самооценка)

- держится ли изменение (gate + I1..I5);
- **число тихих сломов незаписанных инвариантов** (приоритетный киллер);
- обращений к автору (контаминация/неполнота);
- распределение A vs B по I1..I5;
- какие из I1..I5 опросник **переоткрыл** сам (мера легибельности артефактов).

## 8. Роли и handoff

- **Lab:** владеет этим протоколом; не строит.
- **Автор (сторона A):** §3 пред-регистрация + судит **по исходу** (не «покрыл ли опросник»).
- **RTM-координатор (сторона A):** исполняет build в операционном треке; пишет результат в `Evidence-Log`
  как **E-022** (по факту исполнения), с A/B-классификацией и статусом ЗАРАБОТАНО/опровергнуто.
- **Изоляция:** прогон едет на реальной нужде RTM; Метод наблюдает, не рулит.
