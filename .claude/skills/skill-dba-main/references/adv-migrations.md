# DBA Skill: Advanced Migrations & Refactoring

When performing schema changes or complex database migrations, always ensure data safety and minimal downtime, especially on production-like instances or large tables.

## 1. Safe Schema Refactoring (Zero Downtime Mindset)

### 1.1 Modifying Large Tables (Millions of Rows)

Directly altering a large table (e.g., `ALTER TABLE orders ADD COLUMN status VARCHAR(20)`) locks the table in many engines (often taking minutes or hours) and can cause catastrophic application downtime.

**The "Shadow Table" Approach (Universal Schema):**

```sql
-- 1. Create the new table with the updated schema (e.g., adding an index or changing a type)
CREATE TABLE orders_new (
    id INT PRIMARY KEY,
    status VARCHAR(20),
    new_column BIGINT -- The change we wanted
);

-- 2. Create triggers to sync live changes
CREATE TRIGGER sync_insert AFTER INSERT ON orders
FOR EACH ROW INSERT INTO orders_new (id, status) VALUES (NEW.id, NEW.status);

-- 3. Backfill data in small, non-blocking batches
INSERT INTO orders_new (id, status)
SELECT id, status FROM orders WHERE id BETWEEN 1 AND 1000;
-- ... repeat for next chunks ...

-- 4. The Atomic Swap (Zero downtime lock)
-- In MySQL/Postgres:
RENAME TABLE orders TO orders_old, orders_new TO orders;
-- In SQLite:
-- ALTER TABLE orders RENAME TO orders_old;
-- ALTER TABLE orders_new RENAME TO orders;

-- 5. Cleanup
DROP TABLE orders_old;
```

### 1.2 Changing Data Types (e.g., INT to BIGINT)

If a table is approaching the maximum value of an `INT` (2,147,483,647), do NOT simply run `ALTER TABLE ... MODIFY COLUMN id BIGINT;` on a massive live table. It will rewrite the entire table and all its indexes, causing massive I/O and locking.

**Safe Approach:**

1. Add a new column: `ALTER TABLE users ADD COLUMN id_new BIGINT;`
2. Run a background script to update `id_new` with the value of `id` in small batches.
3. Update application code to write to both columns.
4. Drop `id` and rename `id_new` to `id`. (This still requires brief locks but is safer than rewriting the table).
   _Note: Tools like `pt-online-schema-change` (Percona) or `gh-ost` (GitHub) automate this in MySQL. If these are unavailable, do it manually._

### 1.3 Renaming Columns

In older MySQL versions or SQLite, renaming a column might require recreating the table (see 1.1). In modern MySQL (8.0+) and PostgreSQL, `ALTER TABLE ... RENAME COLUMN old_name TO new_name;` is an instant metadata change. Always verify the DB engine version before suggesting an approach.

## 2. Engine-Specific Migration Gotchas

When migrating schemas or queries between engines (e.g., SQLite to MySQL, or MySQL to Postgres), be aware of these critical differences:

### 2.1 Auto-Incrementing Primary Keys

- **SQLite**: `id INTEGER PRIMARY KEY AUTOINCREMENT`
- **MySQL**: `id INT AUTO_INCREMENT PRIMARY KEY`
- **PostgreSQL**: `id SERIAL PRIMARY KEY` (or `id INTEGER GENERATED ALWAYS AS IDENTITY`)
- **SQL Server**: `id INT IDENTITY(1,1) PRIMARY KEY`
- **Oracle**: `id NUMBER GENERATED BY DEFAULT AS IDENTITY` (12c+)

### 2.2 Date and Time Functions

- **Current Time**:
  - SQLite: `CURRENT_TIMESTAMP` or `datetime('now')`
  - MySQL: `NOW()` or `CURRENT_TIMESTAMP`
  - PostgreSQL: `CURRENT_TIMESTAMP` or `NOW()`
  - SQL Server: `GETDATE()` or `SYSDATETIME()`
  - Oracle: `SYSDATE` or `CURRENT_TIMESTAMP`
- **Date Math**:
  - SQLite: `date(created_at, '+1 day')`
  - MySQL: `DATE_ADD(created_at, INTERVAL 1 DAY)`
  - PostgreSQL: `created_at + INTERVAL '1 day'`
  - SQL Server: `DATEADD(day, 1, created_at)`
  - Oracle: `created_at + INTERVAL '1' DAY` (or simply `created_at + 1`)

### 2.3 String Concatenation

- **SQLite / PostgreSQL / Oracle**: `first_name || ' ' || last_name`
- **MySQL**: `CONCAT(first_name, ' ', last_name)` (Using `||` in MySQL behaves as a logical OR by default unless `PIPES_AS_CONCAT` mode is enabled).
- **SQL Server**: `first_name + ' ' + last_name` or `CONCAT(first_name, ' ', last_name)`

### 2.4 Boolean Types

- **SQLite**: Does not have a native `BOOLEAN` type; uses `INTEGER` (0 or 1).
- **MySQL**: Has a `BOOLEAN` synonym, but it actually stores as `TINYINT(1)`.
- **PostgreSQL**: Has a true `BOOLEAN` type (`TRUE`/`FALSE`).
- **SQL Server**: Uses `BIT` (1, 0, or NULL). There is no native `BOOLEAN` in T-SQL.
- **Oracle**: Lacks a native `BOOLEAN` in SQL (uses `NUMBER(1)` or `VARCHAR2(1)` with a `CHECK` constraint).

### 2.5 Constraints and `ALTER TABLE`

- **MySQL/PostgreSQL/SQL Server**: Support extensive `ALTER TABLE` commands (e.g., `DROP COLUMN`, `ADD CONSTRAINT`).
  - **[MySQL] Online DDL**: Use `ALGORITHM=INPLACE, LOCK=NONE` when possible for large alterations without blocking inserts.
  - **[PostgreSQL] Transactional DDL**: Schema changes (`ALTER`, `CREATE`, `DROP`) can be wrapped in a transaction (`BEGIN; ... COMMIT;`). If something fails, the schema change safely rolls back. This is a massive safety advantage over MySQL.
  - **[PostgreSQL] Online Index Creation**: ALWAYS use `CREATE INDEX CONCURRENTLY` on live production tables. A standard `CREATE INDEX` locks the table against writes.
  - **[SQL Server] Online Index Creation**: Use `CREATE INDEX ... WITH (ONLINE = ON)` in Enterprise editions.
  - **[PostgreSQL] Adding Columns with Defaults**: In Postgres 11+, `ALTER TABLE ... ADD COLUMN ... DEFAULT ...` is instant and does not rewrite the table.
- **SQLite**: Historically very limited `ALTER TABLE` support. Dropping columns or changing constraints usually requires the "Shadow Table" approach (create new, copy data, drop old, rename new). _(Note: SQLite 3.35.0+ added support for `ALTER TABLE ... DROP COLUMN`)._

### 2.6 MySQL 8.0 / 8.4 Gotchas (The "Modern" Traps)

When migrating from MySQL 5.7 to 8.0/8.4 or when developing on modern versions, watch out for these massive "gotchas":

- **[MySQL 8.0] Implicit Sorting Removed**: In MySQL 5.7, a query with `GROUP BY` would implicitly sort the results by that column. In MySQL 8.0, **this implicit sorting was completely removed** for performance. Any query relying on `GROUP BY` to return ordered results MUST add an explicit `ORDER BY`.
- **[MySQL 8.0] New Reserved Words**: Words like `RANK`, `SYSTEM`, `CUBE`, `LEAD`, `LAG`, `WINDOW`, and `OVER` are now reserved. If a legacy schema has a table or column named `rank`, any query touching it will throw a syntax error unless wrapped in backticks (`` `rank` ``).
- **[MySQL 8.0] Collation Mismatches**: The default charset is now `utf8mb4` with the collation `utf8mb4_0900_ai_ci` (based on Unicode 9.0). If you `JOIN` a modern table with an older `utf8mb4_general_ci` table, the query will crash with an "Illegal mix of collations" error.
- **[MySQL 8.4 LTS] Authentication Removed**: In MySQL 8.4, the classic authentication plugin `mysql_native_password` (used by millions of old PHP, Python, and Node.js drivers) was **removed**. The default is now strictly `caching_sha2_password`. Applications using ancient drivers will fail to connect entirely to MySQL 8.4+.

### 2.7 PostgreSQL Gotchas (Version Migrations & Traps)

When migrating older PostgreSQL instances (PG 11 or 12) to modern versions (PG 13-17), or auditing legacy schemas, watch out for these massive "gotchas":

- **[PostgreSQL 12] The Death of OIDs**: Prior to PG 12, tables could be created `WITH OIDS` (a hidden system object ID for every row). In PG 12, this was **completely removed**. Legacy database dumps or ORM scripts relying on `OIDs` will crash immediately when restored on modern Postgres.
- **[PostgreSQL 15] The `public` Schema Security Trap**: Historically, any connected user could create tables in the default `public` schema. In **PG 15**, this default `CREATE` privilege was **revoked for security**. CI/CD pipelines or applications that dynamically create tables without explicit schema ownership will fail with `Permission denied for schema public`.
- **[PostgreSQL] `SERIAL` vs `IDENTITY`**: Never write new code using the legacy `SERIAL` pseudo-type. If you manually insert an ID into a `SERIAL` column, the underlying sequence doesn't know, causing primary key violations on the next insert. ALWAYS use the SQL-standard `INT GENERATED ALWAYS AS IDENTITY` (available since PG 10), which prevents manual overrides unless explicitly forced.
- **[PostgreSQL 13+] B-Tree Deduplication**: PG 13 introduced automatic index deduplication, making B-Tree indexes significantly smaller and faster. However, if you upgrade from PG 12 via `pg_upgrade`, existing indexes are NOT automatically deduplicated. You MUST manually run `REINDEX INDEX index_name` to get the massive performance and space benefits.

### 2.8 Oracle Gotchas (11g vs 12c vs 23ai)

When auditing or migrating Oracle databases across its major epochs, keep these structural shifts in mind:

- **[Oracle 12c+] The End of Sequence-Trigger Hell**: Prior to 12c, creating an auto-incrementing ID required creating a `SEQUENCE` and a `BEFORE INSERT TRIGGER` for every single table. In 12c, Oracle finally introduced `GENERATED AS IDENTITY`. Always recommend refactoring legacy sequence-triggers to native identity columns when migrating.
- **[Oracle 12c+] Extended VARCHAR2 Size**: Historically, `VARCHAR2` was strictly limited to 4000 bytes. In 12c, this was extended to 32767 bytes (if the DBA enables the `MAX_STRING_SIZE = EXTENDED` parameter).
- **[Oracle 23ai] The `BOOLEAN` Miracle**: For decades, Oracle SQL lacked a true `BOOLEAN` data type, forcing developers to use `NUMBER(1)` (0/1) or `VARCHAR2(1)` ('Y'/'N'). Finally, in Oracle 23c/23ai (2023), a native `BOOLEAN` type was introduced. Suggest modernizing schema flags if running 23ai.
- **[Oracle 23ai] `GROUP BY` Alias Support**: Before 23c, you could not use a `SELECT` alias in the `GROUP BY` or `HAVING` clause (you had to repeat the entire expression). Oracle 23ai finally supports `GROUP BY alias`.

### 2.9 SQLite Gotchas (Legacy vs Modern)

SQLite is constantly updated, but because it's embedded, applications often run on extremely old versions. Be aware of these turning points:

- **[SQLite 3.37+] Strict Typing (`STRICT` Tables)**: Historically, SQLite used "Flexible Typing" (Manifest Typing), meaning you could literally insert the string `"hello"` into an `INTEGER` column and it wouldn't complain. In version 3.37.0 (2021), `STRICT` tables were introduced. Always append `STRICT` to new `CREATE TABLE` statements (e.g., `CREATE TABLE t(id INT) STRICT;`) to enforce data integrity.
- **[SQLite 3.35+] `DROP COLUMN` Support**: For 20 years, SQLite could not drop a column. You had to do a 5-step table recreation process. In 3.35.0 (2021), `ALTER TABLE ... DROP COLUMN` was finally added. Check the engine version before proposing the complex "Shadow Table" migration.
- **[SQLite 3.45+] JSONB**: SQLite has had JSON support for years, but in 3.45.0 (2024), a massive rewrite introduced `JSONB` (a binary JSON format) that significantly speeds up JSON processing, similar to Postgres.

### 2.10 SQL Server Gotchas (Version Traps)

When moving across Microsoft SQL Server versions (2016, 2019, 2022), watch out for these traps:

- **[SQL Server 2022] The `STRING_SPLIT` Trap**: A massive gotcha for T-SQL developers. `STRING_SPLIT` was introduced in 2016, but it **did not guarantee the order** of the returned split strings. In SQL Server 2022, Microsoft finally added the `enable_ordinal` parameter. If code relies on the order of split strings without this parameter, it's a critical bug waiting to happen.
- **[SQL Server 2019] UTF-8 Support**: Prior to 2019, if you wanted Unicode support, you had to use `NVARCHAR` (which consumes 2 bytes per character, doubling storage size). SQL Server 2019 introduced native UTF-8 collations (e.g., `Latin1_General_100_CI_AS_SC_UTF8`), allowing standard `VARCHAR` to store emojis and international characters efficiently.
- **[SQL Server 2022] `GREATEST` and `LEAST`**: Standard SQL functions to find the max/min in a list of columns were inexplicably missing from SQL Server until version 2022. Legacy code relies on massive `CASE WHEN` statements which can now be refactored.
