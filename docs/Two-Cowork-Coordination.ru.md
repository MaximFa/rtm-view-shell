только швом МЕЖДУ двумя Cowork'ами. Английская версия: `docs/Two-Cowork-Coordination.md`.

## 1. Топология

Два экземпляра Cowork, каждый = свой клон/worktree репо + свой внутренний `.coord/` bus +
**один координатор** (внутри полностью работает §42).

| Cowork | Набор ролей (карта 9 ролей специализации) | Рабочая ветка |
|---|---|---|
| **A — «Backend»** | RTM Server, Metrics, DBA, Devops | `v2-backend` |
| **B — «Frontend»** | Shell, UX-UI, Widget, QA | `v2-frontend` |
| **Security** | Общий релиз-gate — **обязательный ack перед любым прод-релизом** | на интеграции (§5) |

- **Интеграционный trunk:** `v2` на origin (общая релизная ветка).
- **Release-captain:** один назначенный координатор гонит кросс-барьер и прод-пуш.
  По умолчанию = **Cowork-A** (владеет Devops + релиз-тулзами: prod-release, оркестраторы, Compare-ToBaseline).

---

## 2. Почему git, а не общий mount

Mount — наш *ненадёжный* канал (L-SC-04 async-дропы кросс-view, L-SC-10 фантомы); файловая
шина `.coord/` — best-effort даже внутри ОДНОГО Cowork'а (это и есть стоящий **[CRITICAL]**-бэклог).
Между двумя экземплярами mount-канал был бы строго хуже.

Git — наш *доказанный* канал (L-SC-18 «git = истина», L-SC-19 надёжность append). Поэтому:

- Пересечение по файлу между ветками всплывает как **git merge conflict — безопасно и восстановимо**,
  в отличие от **тихого lost-update** на общем mount'е (L-SC-09 — второй писатель молча затирает первого).
- Сообщения координатор↔координатор едут **коммитами** — упорядочены, атомарны, без дропов и фантомов.

---

## 3. Кросс-канал — orphan-ветка `coord`

Отдельная git-ветка **`coord`** только с координационными файлами (без кода) — держит кросс-канал
вне `v2` и почти без конфликтов. Оба координатора pull/push её.

Файлы в `.coord/cross/` на ветке `coord`:

| Файл | Назначение |
|---|---|
| `ownership.md` | карта модуль→Cowork + **таблица единственного владельца seam-файлов** (кросс-истина, §6) |
| `inbox-coord-A.md`, `inbox-coord-B.md` | направленные кросс-сообщения (формат блока = §11 session-coord) |
| `ledger.md` | append-only кросс-события: пуш ветки, интеграция, барьер, релиз |
| `barrier.md` | состояние активного кросс-релиз-барьера (наличие = **по содержимому** `-s`+`cat`, никогда `-f`, L-SC-10) |

**Хэндшейк (каждая запись в кросс):**
```
git fetch origin coord  ->  rebase локального coord  ->  читаю  ->  действую
  ->  append сообщения (Python + os.fsync)  ->  commit  ->  git push origin coord
```
Пуш отклонён (сосед запушил раньше) -> `fetch` + `rebase` (append-only авто-мёржится) -> retry.
**Бэкстоп** если даже git занят: координатор сообщает оператору в чат, тот релеит (оператор + git —
надёжные каналы; зеркало L-SC-19).

---

## 4. Ветки и интеграция

- Каждый Cowork работает на своей ветке и пушит в origin **после своего L1 §42.7-барьера**.
- **L2-интеграция:** release-captain мёржит `v2-backend` + `v2-frontend` -> `v2`.
  Частота: **ежедневно / по завершении эпика** — мелкие дельты = меньше швов-конфликтов.
- После интеграции оба Cowork'а `git merge origin/v2` обратно в свою ветку (держим дрейф малым).

---

## 5. Двухуровневый push/релиз-барьер

**L1 (внутри Cowork'а):** существующий §42.7-барьер внутри каждого Cowork'а -> пуш его собственной
ветки в origin. Без изменений.

**L2 (кросс-интеграция / релиз):**
1. Captain пишет `barrier.md` на `coord`: предлагает интегрировать `A@<sha>` + `B@<sha>` -> `v2`.
2. Каждый координатор **кросс-ack'ает** (его ветка чистая и L1-запушена на `<sha>`) через
   свой кросс-инбокс / `ledger.md`.
3. Captain: fetch обе ветки -> merge в `v2` -> развести **швы-конфликты** с соседом (через кросс-инбокс)
   -> кросс-сборка / интеграционные тесты -> **Security ack (обязательно)** -> push `v2` ->
   нарезать прод-релиз если нужно.
4. Оба Cowork'а ресинкаются из `v2`. Captain журналит `INTEGRATED` / `RELEASED` в `ledger.md`.

## 6. Seam-файлы — правило единственного владельца

Файлы, которые легитимно трогают обе стороны, получают **одного владельца** в `ownership.md`;
не-владелец просит изменение через кросс-инбокс соседа (кросс-Cowork версия §9 FIFO-очереди).

Дефолты (зафиксировать в `ownership.md`):

| Seam-файл | Владелец | Правило |
|---|---|---|
| `CLAUDE.md` | captain | append-only §-секции авто-мёржатся; правка СУЩЕСТВУЮЩЕЙ общей секции -> только captain |
| `src/CcDashboard.Web/Program.cs` | B (Frontend/Shell host) | не-владелец просит через кросс-инбокс |
| `db/schema.sql`, `db/baseline.sql` | A (DBA) | регенерит только A через Export-All |
| `src/.../RtsEntities.cs` | A (DBA/RTM) | — |
| `NavMenu.razor`, layout/CSS-токены | B (UX-UI/Shell) | — |

**Целый релиз остаётся в ОДНОМ Cowork'е** — не разрезать релиз между двумя (напр. апгрейд
Server-234 целиком в A).

## 7. Роль оператора над двумя Cowork'ами

Сессии не поллят; оператор — **планировщик над ОБОИМИ приложениями**, теперь ещё и релеит поки
между двумя экземплярами Cowork. Новые кросс-команды (префикс `коорд:`, внутри-Cowork набор не меняется):

| Команда | Кому | Действие |
|---|---|---|
| `коорд: кросс-статус` | координатору | прочитать ветку `coord` -> доложить кросс-состояние (ветки, барьер, долг интеграции) |
| `коорд: кросс-ack` | координатору | подтвердить свою ветку чистой + L1-запушенной на `<sha>`, написать ack на `coord` |
| `коорд: интеграция` | captain'у | предложить / выполнить L2-интеграцию (§5.1–5.4) |
| `коорд: релиз` | captain'у | прогнать L2-релиз-барьер вкл. **Security ack** + прод-пуш |

## 8. РАЗВЁРТЫВАНИЕ Cowork-B НА ВТОРОМ КОМПЬЮТЕРЕ

### 8.1 Что нужно на втором компе
- **Claude desktop (Cowork mode)** — само приложение.
- **Git** + доступ к тому же `origin`, что и на первом компе (один remote = точка синхронизации).
- **.NET 8 SDK** — локальная сборка/тесты Shell.
- *(опц.)* **PostgreSQL 18** (`C:\Program Files\PostgreSQL\18`) + **Memurai/Redis** — если на этом
  компе будете локально гонять Shell для QA. Для чисто-кодовой/ревью-работы не обязательно.
- **Тот же путь папки**, что в CLAUDE.md: `D:\Claude\Projects\RTM View Shell`. CLAUDE.md хардкодит
  `D:\` — используйте тот же путь, иначе инструкции в нём не совпадут.

### 8.2 Однократно (на первом компе / captain) — нарезать ветки
```bash
# из существующего v2
git checkout v2 && git pull
git checkout -b v2-frontend && git push -u origin v2-frontend
git checkout -b v2-backend  && git push -u origin v2-backend     # если ещё нет

# кросс-канал: orphan-ветка coord (только координационные файлы, без кода)
git checkout --orphan coord
git rm -rf .                         # очистить рабочее дерево от кода
mkdir -p .coord/cross
printf '# ownership — модуль->Cowork + seam-владельцы\n' > .coord/cross/ownership.md
printf '# inbox координатора A\n'  > .coord/cross/inbox-coord-A.md
printf '# inbox координатора B\n'  > .coord/cross/inbox-coord-B.md
printf '# cross ledger (append-only)\n' > .coord/cross/ledger.md
git add .coord/cross && git commit -m "coord: bootstrap cross-channel"
git push -u origin coord
git checkout v2-backend               # вернуться на рабочую ветку A
```

### 8.3 На втором компе — поднять Cowork-B
```bash
# 1. Клонировать репо в ТОТ ЖЕ путь
git clone <origin-url> "D:\Claude\Projects\RTM View Shell"
cd "D:\Claude\Projects\RTM View Shell"

# 2. Перейти на свою рабочую ветку
git fetch origin
git checkout v2-frontend

# 3. Подтянуть кросс-канал ОТДЕЛЬНЫМ worktree (чтобы не переключать рабочую ветку ради записи в coord)
git worktree add "D:\Claude\Projects\RTM-coord" coord
```
Затем:
- Открыть **Claude desktop -> Cowork -> подключить папку** `D:\Claude\Projects\RTM View Shell`.
- Называть сессии с префиксом **`RTM`** (§0.8).
- Зарегистрировать координатора: в новой сессии **`коорд: ты координатор`** — он прочитает
  CLAUDE.md + скилл `session-coord` + этот документ + сделает аудит шины.

### 8.4 Кросс-канал через worktree (рекомендация)
Чтобы писать в `coord`, не дёргая рабочую ветку, держите `coord` отдельным worktree
(`D:\Claude\Projects\RTM-coord`). Цикл записи координатора:
```bash
cd "D:\Claude\Projects\RTM-coord"
git pull --rebase origin coord
# ... append в .coord/cross/<файл> через Python+fsync ...
git add .coord/cross && git commit -m "coord: <что>" && git push origin coord
```

### 8.5 Проверка развёртывания
- `git branch -a` показывает `v2-frontend`, `v2-backend`, `coord`.
- `CLAUDE.md` и `.claude/skills/` на месте (пришли с клоном).
- `git fetch origin coord` работает (доступ к кросс-каналу есть).
- Оба компа умеют push/pull origin под своими ветками.
- В Cowork-B `коорд: ты координатор` отвечает аудитом шины (значит, скиллы и CLAUDE.md прочитаны).

### 8.6 Что мигрирует куда
- Текущий Cowork (этот) -> **Cowork-A (Backend)**: сессии `devops-2`, `metrics-2` подходят прямо;
  `daytrend-2` (тракт данных RTM/DB/widget) остаётся в A, его касания Shell-компонентов = швы -> кросс-запрос в B.
- Новый комп -> **Cowork-B (Frontend)**: Shell / UX-UI / Widget / QA; перенести туда `test-5` (QA).
- **Апгрейд Server-234 завершить в A до/вне раздела** — релиз не резать на лету.

## 9. Открытые дефолты — на слово оператора

- Имена веток: `v2-backend` / `v2-frontend` vs `v2-a` / `v2-b`.
- Release-captain = Cowork-A (Backend) — владеет Devops. (Альтернатива: ротация, или релиз у B.)
- Частота интеграции: ежедневно vs по эпику.
- Носитель кросс-канала: orphan-ветка `coord` (рекомендую) vs `.coord/cross/` коммитом на `v2`.
- Security: отдельный (3-й) Cowork или роль-скилл, подгружаемый captain'ом на L2.
