## Часть A

### Q1. Терминал говорит, что ничего не произошло.

**ВЫВОД: не установлено. Присланный вывод не является доказательством НИ доставки, НИ потери.**

**Чего стоит присланный вывод как доказательство.** Ничего — по всем трём строкам:
- `git add <файл>` молчит и при успехе, и при no-op, и когда путь **проигнорирован** (`.gitignore`),
  и когда путь не существует. Тишина `add` — не сигнал.
- «no changes added to commit» говорит ровно одно: **индекс равен HEAD**. Это истинно и когда правки
  нет, и когда правка **уже в HEAD** (закоммичена раньше), и когда путь игнорируется, и когда правка
  легла в другой файл/другой клон.
- «Everything up-to-date» — про **ref**, а не про содержимое: локальный `<ветка>` совпал с
  `origin/<ветка>`. Истинно и когда всё запушено, и когда локально ничего не коммитилось вовсе.
- И сверху: «моей правки нет в списке изменённых» — это вывод `status`, т.е. сравнение с индексом.
  А `status` через маунт запускать вообще нельзя (§3, `index.lock`), так что этот пункт и получен-то
  сомнительным путём.

Общее свойство: все три строки — это отчёты о **разности состояний**, и каждая совместима и с «дошло»,
и с «не дошло». Ни одна не читает содержимое файла в дереве коммита. Это ровно тот класс, что урок
2026-06-14 (mount false-M) и §0.1 «tool success ≠ delivery», только вывернутый наизнанку:
здесь инструмент говорит «ничего не произошло», а «не произошло» — не факт.

**Единственная сверка, которая закрывает вопрос — процедура (не рассуждение):**

```
git rev-parse <ветка>:<путь>        # blob-SHA файла В КОММИТЕ ветки
git hash-object -w -- <путь-на-диске>  # (или без -w) SHA содержимого на диске
```
Равны → правка В репозитории. Не равны → нет. Дальше, если нужно, где именно:
```
git cat-file -p <ветка>:<путь> | grep -n '<маркер правки>'   # содержимое, не статус
git rev-parse <ветка> && git rev-parse origin/<ветка>        # два ref: пуш или нет
git check-ignore -v -- <путь>                                # игнор или нет
```
Т.е. **сверять содержимое blob'а по object store против содержимого на диске**, а не читать отчёты
о разности. Числа строк — не критерий (§3): байты/SHA.

**Все состояния мира, дающие ровно такой вывод:**
1. Правка **уже закоммичена и запушена** раньше (в HEAD и в origin) — всё три строки честны, работа цела.
2. Путь **игнорируется** (`.gitignore`) — здесь это норма проекта: `.coord/*` под `*`, и `add` по нему
   молча ничего не делает (урок 2026-07-03, «нетрекаемое не сохранено»). Работа на диске, в git её нет.
3. Правки **на самом деле нет**: писали Edit-tool'ом (забанен) и он молча не дописал; писали в другой
   файл; писали в **другой клон** (`C:\...\Documents\...` — стейл, §инит) — git в D:\ честно ничего не видит.
4. Правка есть, но **байтово идентична** тому, что уже в HEAD (пере-записали то же самое).
5. `add` отработал **не по тому пути** (опечатка, относительный путь из другого cwd, регистр/пробел
   в «RTM View Shell»); файл не существовал по указанному пути.
6. Команды выполнены **не в том репозитории/не в той ветке**: `on branch v3` — но правка ушла в другую
   ветку/worktree, или клон вообще другой.
7. `commit` отработал **раньше** (предыдущим шагом) и правка ушла отдельным коммитом, а этот `add`
   уже no-op; `push` тогда честно up-to-date.
8. Патологии: `index.lock`/сбитый индекс, `assume-unchanged`/`skip-worktree` на пути, симлинк/иной
   регистр имени на NTFS.
Существенно: **пункты 1, 4, 7 = работа цела; 2, 3, 5, 6 = работа НЕ в репозитории.** Одинаковый вывод.

### Q2. Два предупреждения, которые выглядят одинаково.

**(а) `git add .coord/inbox` — тишина, «нечего коммитить»: РАБОТА ПОТЕРЯНА (не сохранена в git).**
**(б) `git add .claude/skills/role-devops` + «The following paths are ignored… .claude», коммит взял N
файлов: РАБОТА НЕ ПОТЕРЯНА.**

**Почему это разные случаи.** Различие не в громкости сообщения, а в **результате**:
- В (б) git **напечатал предупреждение и всё равно взял N файлов** — предупреждение относится к части
  путей (или к правилу, перебитому исключением/`!`-negation), а коммит содержит непустой набор. Есть
  положительный факт: N > 0 и его можно назвать поимённо.
- В (а) git **промолчал и взял ноль**. `.coord/.gitignore` первой строкой держит `*`, наружу вынесены
  только явные исключения (`protocols/**`, `migration/**` и — с 2026-08-17 — `coordinator_handoff.md`,
  `rejects.md`, `features.md`, `backlog.md`). `inbox/` в список исключений НЕ входит намеренно.
  Значит `add` по нему — тихий no-op. Тишина здесь означает «ничего», а не «всё хорошо».
Т.е. это разные случаи ровно потому, что **шумность вывода не коррелирует с исходом**: громкое
предупреждение сопровождало успех, а тишина — потерю. Читать надо исход, а не тон.
Именно на этом обжёгся проект 2026-07-03: `git clean` унёс нетрекаемый пакет TechWriter'а.

**Цена ошибки в обе стороны:**
- Принять (а) за «сохранено» → работа живёт только на диске одного клона. Любой `clean`/переустановка/
  переезд аккаунта — и её нет, восстановить неоткуда (object store её не держал никогда). Это
  необратимая потеря — самый дорогой исход, и он уже случался.
- Принять (б) за «потеряно» → ложная тревога: перекоммит, лишний цикл, возможно порча уже
  корректного дерева суетливым «исправлением» (reset/clean по живому). Дорого, но **обратимо**.
Асимметрия ясная: молчание — опаснее шума, и презумпция должна быть «не сохранено, пока не доказано».

**Механический различитель (не эвристика).** Не смотреть на текст предупреждения вообще. Смотреть на
**состав коммита по object store**:
```
git diff-tree --no-commit-id --name-only -r <коммит>       # что коммит реально несёт
git rev-parse <ветка>:<конкретный/путь>                    # blob есть? -> путь внутри
git ls-tree -r <ветка> -- <каталог>                        # непусто? -> каталог внутри
git check-ignore -v -- <путь>                              # если пусто: правило и его файл:строка
```
Критерий: **для каждого конкретного пути, который я считаю доставленным, `rev-parse <ветка>:<путь>`
обязан отдать blob-SHA, а этот SHA — совпасть с `hash-object` от диска.** Ноль путей в коммите или
отсутствие конкретного пути = потеря, независимо от того, что печатал `add`.

### Q3. Проверка, которая врёт «да».

Грепнуть файл на маркер после записи — это проверка того, что **строка присутствует в некотором тексте**,
а вовсе не того, что **правило внесено и действует**. Ситуации, где такой «проход» не стоит ничего
(нужно две — привожу больше, они разного рода):

1. **Грепнули не тот носитель.** Файл прочитан из буфера/кэша маунта, а на NTFS легло усечённое
   (§0.3 CLAUDE.md: без `os.fsync` `tail`/`wc` читают тот же кэш и «подтверждают» ложь). Или грепнули
   диск, а правило нужно **в git** — и оно там не оказалось (Q2(а)). Или грепнули копию в стейл-клоне.
2. **Маркер существовал и до правки.** Совпало с примером, цитатой, старой формулировкой, строкой в
   оглавлении, собственным текстом в комментарии «не делать так». Без снимка «до» count-после сам по
   себе не свидетельствует ни о чём.
3. **Маркер есть, а правило — нет.** Строка легла в закомментированный блок, в блок примера, в раздел,
   помеченный superseded/архив, в другой файл того же имени; либо легла корректно, но текст
   противоречив (рядом стоит старая, не удалённая формулировка, и норма стала двусмысленной).
4. **Врёт сам предикат.** Паттерн с незаэкранированным спецсимволом, `grep` без `-F`, отличие в
   NBSP/дефисе/BOM/CRLF, `-c` считает СТРОКИ, а не совпадения (у меня в §C item 1 это дало 59 против 48
   — та же величина, два разных числа). Или наоборот: `grep -c` вернул 0 из-за опечатки в паттерне, и
   «не сошлось» объявлено там, где всё сошлось.

**Чтобы это стала проверка, к ней надо добавить:**
- **привязку к носителю истины**: сверять blob по object store (`git cat-file -p <ветка>:<путь>`),
  и — если предмет ещё и на диске — отдельно сверить `sha256` диска против blob'а (я так и сделал
  ниже: handoff, CLAUDE.md, оба скилла, инит, сам этот тест);
- **дельту, а не абсолют**: count ДО и ПОСЛЕ, ожидаемая разница названа заранее;
- **уникальность и место**: `grep -n` — где именно строка, в живом ли разделе; отсутствие
  конкурирующей старой формулировки (грепать и на неё тоже, ожидая 0);
- **отрицательный контроль**: тот же греп по заведомо-не-содержащему файлу обязан дать 0 — иначе врёт
  паттерн, а не файл;
- **критерий, сформулированный ДО прогона**, в терминах «сколько и где», а не «есть ли что-нибудь».

**Почему куратор ошибся на `git check-ignore -v`.** Он взял **факт вывода** за критерий: «напечатало
четыре строки → четыре файла игнорируются → правило не сработало». Но `check-ignore -v` — это
инструмент **объяснения**, а не приговора: с `-v` он печатает строку `<файл-правил>:<номер>:<шаблон>`
для КАЖДОГО пути, чью судьбу определило какое-то правило, — **включая правило-исключение** `!pattern`.
Строка вида `.coord/.gitignore:14:!coordinator_handoff.md   .coord/coordinator_handoff.md` означает
ровно ОБРАТНОЕ объявленному: путь вынут из-под игнора именно новым правилом. Четыре строки на четырёх
файлах — это четыре подтверждения, что правило и есть тот, кто решает их судьбу. Классический
«проверка врёт», только в другую сторону: он читал **наличие вывода**, а не **его содержание**, и не
посмотрел на exit-code (без `-v` `check-ignore` печатает лишь реально игнорируемые и кодом 1 сообщает
«ни один не игнорируется»).

**Что надо было взять критерием вместо этого вывода.** Не поведение `check-ignore`, а **результат в
object store**: попадают ли эти четыре файла в дерево ветки.
```
git ls-tree -r <ветка> -- .coord/            # ожидать: все четыре пути присутствуют
git rev-parse <ветка>:.coord/coordinator_handoff.md   # ожидать: blob-SHA
```
Я это и прогнал (Часть C ниже): `.coord/coordinator_handoff.md` = blob `0f6beaa`, `rejects.md` =
`819da64`, `features.md` = `5667540`, `backlog.md` = `e1e9e5c` — все четыре В ДЕРЕВЕ `v3`.
Правило сработало. Если бы нужен был всё-таки `check-ignore` — критерием служит **exit-code** и то,
`!`-правило в строке или обычное, а не количество напечатанных строк.

### Q4. Ты не знаешь, где ты.

**На каком аккаунте работает сессия — я из прочитанного НЕ вывожу и не устанавливаю.**

**Класс факта.** Это факт **о среде исполнения** (runtime/окружение сессии), а не о репозитории.
Тот же класс, что «какая сегодня дата», «какой инстанс меня исполняет», «поднят ли device_bash» —
свойства мира вокруг процесса, а не содержимого рабочего дерева.

**Почему object store тут бессилен — принципиально.** Git хранит только то, что в него положили:
содержимое файлов, деревья, коммиты, их авторов. Аккаунт, с которого запущена ЭТА сессия, в дерево
не записывается ничем и никем; **пина под него не существует в принципе**. Документ, описывающий
переключение аккаунтов (рунбук миграции, кросс-аккаунтный канал, чужой хендоф), доказывает лишь, что
такой документ написан, — но не то, что я нахожусь ПОСЛЕ описанного в нём перехода. Хуже: такие
документы читаются при подъёме ВСЕГДА, на любом аккаунте, поэтому они одинаково «подтверждают» обе
взаимоисключающие гипотезы — то есть не различают их вовсе, а значит доказательной силы имеют ноль.
Ровно это и произошло 2026-08-17: сессия прочитала кросс-аккаунтный канал и записала себе «поднят на
ВТОРОМ аккаунте»; оператор её там не поднимал, и ложный факт ушёл в git.

**Норма §3 инита, которая это регулирует** (две части, обе применимы):
- «**АККАУНТЫ — НЕ ТВОЁ ДЕЛО.** Топология — исключительно ведение КУРАТОРА. Ты про неё не рассуждаешь,
  не записываешь её в свой сессионный файл и не упоминаешь в отчётах. Встретил в артефактах разговор
  про переключение, "второй аккаунт", кросс-аккаунтный канал — это адресовано не тебе, прочитал и
  прошёл мимо.»
- «**НЕ ВЫВОДИ СРЕДУ ИЗ ДОКУМЕНТОВ, КОТОРЫЕ ЧИТАЕШЬ.** … Правило: **о среде — только со слов
  оператора; сам не выводи и не угадывай.**»
(Норма продублирована в хендофе как «norm you inherit, init §3, revision aa16664».)

**Как факт вообще может быть установлен:** единственный допустимый источник — **прямое утверждение
оператора** (или куратора, чьё это ведение). Не документ, не догадка, не «узнаваемость обстановки».

**Что я обязан записать про аккаунт в свой сессионный файл: НИЧЕГО.** Ни «второй», ни «первый», ни
«неизвестно» — строки про аккаунт там быть не должно вовсе. Это не пропуск и не осторожная формулировка,
а прямое требование §3: топология не моя территория, и в моих артефактах её нет.
*(Отдельно, честно: оператор в этом подъёме сказал мне про аккаунт словами. Это допустимый источник —
и ровно поэтому я не записываю сказанное в артефакты: разрешено знать со слов, не разрешено вносить
в свой сессионный файл и отчёты. Здесь я упоминаю сам факт только чтобы не выглядело, будто я
скрываю ввод, — в `.coord/sessions/` эта строка не пойдёт.)*

## Часть B — разборы

### UC1. Спека вернулась «сделано».

**Не благословляю на этом отчёте.**

**ПЕРВЫМ проверяю число тестов — 40 — против БАЗОВОГО СЧЁТА, названного в диспатче.** Именно против
диспатча, а не против «звучит правдоподобно» и не против своей памяти: базовый счёт затем и
фиксируется в задании, чтобы у «pass» был знаменатель. Совпало — проверка пройдена частично; стало
меньше — тесты исчезли/отключились/перестали компилироваться и «40/40» описывает усохший набор;
стало больше без объяснения — набор сместился, надо понять чем.
Формально по §A: требую **BUILD=0 + UNIT failed=0 С ЧИСЛАМИ** и **сам сверяю числа**, а не принимаю
формулировку. «build 0» в одиночку, object-store, мой собственный визуал — это полы, а не гейт.

**Как такой отчёт бывает честно написан и при этом неверен** (минимум два — привожу четыре):
1. **Знаменатель усох.** Часть тестов не компилируется/помечена Skip/Ignore/условно исключена — раннер
   честно печатает 40/40 по тем, что остались. Уже случалось ровно так: 2026-07-02 сюита
   `CcDashboard.Tests.Unit` оказалась НЕкомпилирующейся (62 ошибки в Reports/HistoricalReports) — то есть
   весь поток работ по Reports шёл при красной сюите, и никто её не гонял.
2. **«Приложение поднимается» = смоук, а не функциональный гейт.** Старт процесса и загрузка готовых

### UC3. Тебе предлагают написать тест преемнику.

**Не пишу.** Норма (инит §4.4): «**Вступительный тест преемнику ты НЕ пишешь** — его пишет куратор,

**Почему норма именно такая** — три причины, и ни одна не про «так велено»:
1. **Роль, аттестующая собственную линию, не аттестация, а самоподтверждение.** Мой тест проверял бы

   Проверяющий обязан быть внешним по отношению к проверяемой линии.
2. **Тест проверяет ПРЕЕМСТВЕННОСТЬ ДИСЦИПЛИНЫ, а не работу и не доменную экспертизу.** Работа целиком
   в хендофе, экспертиза — в скилле (§A/§B). Дисциплина же общая для всех ролей, и планка у неё должна
   быть ОДНА — иначе каждая роль обзаведётся своим стандартом строгости, и «сдал» перестанет что-либо
   значить между ролями. Единая планка возможна только у того, кто держит все роли сразу, — у куратора.
3. **Соблазн.** Уходящая роль знает, на чём спотыкалась, и естественно пишет тест «под ответ», который
   уже держит в голове, — а преемник, читающий мои же артефакты, узнаёт формулировку и пройдёт узнаванием,
   а не процедурой. Куратор формулирует ловушки так, что знание ответа не помогает (об этом сказано
   и в шапке этого теста).

**Что тогда остаётся моей обязанностью перед преемником и куда кладётся** (инит §4):
1. **Обновить `.coord/coordinator_handoff.md`**: рабочая ветка; пины, которые сходятся ПРЯМО СЕЙЧАС

2. **Записать промахи цикла в `§B LESSONS` своего скилла** — дословно, с источником и датой.

   уроки — сырьё. Я поставляю материал, планку ставит он.
3. **Разослать сигнал хендофа всем живым ролям и собрать их**, проверив, что у каждой живой сессии
   хендоф свежее её последней работы, и доложить, что можно переключаться (после перелогина спрашивать

## 2. Q2(б) — механизм

**Одной фразой: `.gitignore` действует ТОЛЬКО на неотслеживаемые пути — уже отслеживаемые файлы под
игнорируемым каталогом остаются в индексе и продолжают коммититься, а предупреждение относится к тем
путям внутри каталога, что ещё не отслеживаются.**

```
$ grep -n '\.claude' .gitignore
49:.claude/
$ git ls-tree -r --name-only origin/v3 .claude | wc -l
55
$ git ls-tree -r --name-only origin/v3 .claude | head -3
.claude/memory/INDEX.md
.claude/memory/MEMORY.md
.claude/memory/daytend-implementation-insights.md
```

**Почему «игнорируется» и «в git» истинны одновременно** и не противоречат друг другу: это утверждения
о разных множествах. `.claude/` в `.gitignore` — правило для **будущих неотслеживаемых** путей: git не
подхватит их сам и предупредит, если их назвать явно. 55 путей под `.claude` уже **в дереве** `origin/v3`
— они попали туда до правила (или через явный `add -f`), а отслеживаемость сильнее игнора: gitignore
никогда не выкидывает файл из индекса. Отсюда наблюдаемая картина (б): предупреждение напечатано —
про неотслеживаемую часть, — и коммит взял N файлов — отслеживаемую.

Механическое подтверждение того же изнутри самого инструмента:
```
$ git check-ignore -v .claude/skills/role-coordinator/role-coordinator.md
$ echo $?
1
```
Ничего не напечатал и вернул 1 = «не игнорируется» — потому что `check-ignore` по умолчанию **исключает
отслеживаемые пути** из рассмотрения. Тот же файл лежит под `.claude/`, на которое правило есть.
Это и есть строгая граница между двумя множествами, а не эвристика.

И обратная сторона, случай (а): `.coord/inbox/` не отслеживался НИКОГДА, поэтому под `*` в
`.coord/.gitignore` он попадает целиком, `add` по нему — тихий no-op, и коммит берёт ноль. Разница между
(а) и (б) — не в громкости вывода, а в том, есть ли под путём хоть один уже отслеживаемый файл;
проверяется одной командой `git ls-tree -r --name-only <ветка> -- <путь> | wc -l` (55 против 0).

**Чего стоит присланный текст как доказательство: почти ничего.** Он доказывает только то, что

**Единственная сверка, которая закрывает вопрос — сравнение содержимого через object store:**
```
git rev-parse <ветка>:<путь>          # блоб в ветке
git hash-object <путь>                # блоб на диске
git cat-file -s <ветка>:<путь>        # размер в ветке
```
Равны блобы — правка В ВЕТКЕ и диск ей соответствует. Не равны — на диске одно, в ветке другое, и
третьего толкования нет. Плюс `git rev-parse origin/<ветка>` против `git rev-parse <ветка>`: `push`
говорит о рефах, а не о моём файле.

1. Правка уже закоммичена раньше — индекс, дерево и HEAD совпадают, коммитить нечего, пушить нечего.
   Работа НА МЕСТЕ.
2. Правки на диске нет вообще: запись не состоялась (tool success ≠ delivery), или ушла в другой файл,
   или её затёрли. Работа ПОТЕРЯНА.
3. Файл игнорируется (`.gitignore`) — `git add` молчит по path-spec без метасимволов, git видит
   «ничего не добавлено». Работа НА ДИСКЕ, но вне ветки.
4. Правка сделана в ДРУГОМ клоне / другом каталоге / другой ветке, а команды прогнаны здесь.
5. Правка есть, но `git add` получил другой путь (опечатка, регистр, не тот подкаталог) — добавлять
   было нечего, а пользователь читает это как «изменений нет».
6. Файл изменён так, что git не видит разницы: изменены только права/mtime; или запись вернула

### Q2. Два предупреждения, которые выглядят одинаково.

**Механический различитель (не эвристика), после любого `add`:**

### UC3. Мне предлагают написать тест преемнику. Пишу?

**НЕТ, не пишу. Вступительный тест преемнику составляет КУРАТОР — по всем ролям одной планкой.**

**Почему норма именно такая.** Роль, пишущая тест своему преемнику, **аттестует собственную линию**:
она выбирает вопросы из того, что САМА считает важным, и тем самым передаёт преемнику не дисциплину,
а свою картину дисциплины — включая слепые пятна. Дрейфующий инстанс не знает, что дрейфует, и его
тест воспроизведёт дрейф в аттестованном виде: преемник сдаст ровно то, чего предшественник не терял,
и не будет спрошен ровно о том, что тот потерял. Экзамен, который пишет экзаменуемая линия, проверяет
преемственность СЕБЯ, а не нормы. Второе основание: тест проверяет сквозную дисциплину, а она
одинакова для всех ролей — планка должна быть общей, иначе роли разъедутся в требованиях. Сегодня я
вижу цену этого прямо: мой предшественник снят за дрейф, и будь тест его рукой, я сдавал бы его
представление о честности — то самое, которое подменило измерение оговоркой.

3. **Сигнал хендофа всем живым ролям** и сбор их хендофов — после замены спросить будет некого.
4. **Коммит** — иначе всё вышеперечисленное осталось на диске, а диск не ветка.

**Что команда делает на самом деле — формулировка, которую я был обязан дать сразу.**
`check-ignore` печатает **ПОСЛЕДНЕЕ СОВПАВШЕЕ ПРАВИЛО, ВКЛЮЧАЯ ОТРИЦАНИЕ**, — то есть строку на каждый
путь, для которого ПРАВИЛО НАЙДЕНО, а не на каждый путь, который игнорируется. Строка, начинающаяся с
`!`, означает ровно ОБРАТНОЕ печати: путь НЕ игнорируется. Моя прежняя формулировка («печатает строку
на каждый путь, который ИГНОРИРУЕТСЯ») эти два случая склеивает и на строке `A/--no-index` даёт неверный
ответ. Это не описка: склейка «правило найдено» = «файл игнорируется» и есть та самая ловушка.

**Двурежимность, и в каком режиме мой критерий верен, а в каком лжёт.**
- **По умолчанию** команда консультируется с ИНДЕКСОМ и отслеживаемые пути из рассмотрения исключает.
  Поэтому A и C молчат с `rc=1`. В этом режиме «rc=0 → игнорируется» **верно**: печатается только то,
  что действительно игнорируется (B).
- **С `--no-index`** индекс не спрашивается вовсе: команда отвечает, ЧТО СКАЗАЛО БЫ ПРАВИЛО о таком
  пути, а не что произойдёт с ЭТИМ файлом. Здесь A печатается и даёт `rc=0`, будучи трекаемым и НЕ
  игнорируемым. В этом режиме мой критерий **лжёт**, и лжёт ложно-красным: как предикат «потеряно ли»
  он даёт тревогу на каждом трекаемом пути под отрицанием. То есть мой корректив повторял бы осуждаемую
  мной же ошибку именно там, где живёт ловушка.
- Различитель внутри самого вывода, если уж читать вывод: **символ `!` в начале паттерна**. Но брать
  вывод `check-ignore` критерием «сохранено ли» не надо вовсе — вопрос про индекс и дерево, и на него
