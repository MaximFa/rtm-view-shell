# ЧАСТЬ A — ДИСЦИПЛИНА

## Q1. Терминал говорит, что ничего не произошло

**Дошла ли правка — из присланного вывода не следует ни «да», ни «нет».** Три строки описывают состояние
индекса и удалённой ветки, а вопрос задан про содержимое коммита. Это разные предикаты.

**Все состояния мира, дающие ровно такой вывод:**

1. **Правка уже закоммичена раньше** (в прошлом цикле или предыдущей командой). Тогда рабочее дерево ==
   индекс == HEAD, `add` молчит, коммитить нечего, `push` — everything up-to-date, потому что коммит уже
   на удалённом. **Работа НЕ потеряна.**
2. **Правка не легла на диск вообще.** Tool success ≠ delivery: инструмент отчитался, файл не изменился
   (маунт-кэш, запись в другой путь, обрезанная запись, «успешный» вызов без fsync). **Работа потеряна.**
3. **Правка легла, но байт-в-байт совпала с тем, что уже в HEAD** (переписал тем же содержимым). git
   различает по содержимому, а не по mtime. **Терять нечего — изменения нет.**
4. **Путь под `.gitignore`** (или под правилом исключения). `add` без `-f` тихо пропускает — в старых
   версиях git молча, в новых печатает предупреждение (см. Q2). **Работа на диске есть, в репозитории нет.**
5. **Правка сделана не в том рабочем дереве / не в том клоне.** Здесь это реально: есть СТЕЙЛ-клон в
   `...\Documents\...`, который трогать запрещено. **Работа есть, но не там, где смотрит git.**
6. **Правка сделана не в той ветке / после переключения** — коммит существует в другой ветке, текущий
   HEAD её не видит, push этой ветки — up-to-date. **Не потеряна, но не там.**
7. **Файл в индексе помечен `assume-unchanged` / `skip-worktree`** — git не смотрит на рабочее дерево.
   **Работа на диске есть, git её не берёт.**
8. **`push` пушит не ту ветку/не тот remote** (или upstream настроен на другую ссылку) — «up-to-date»
   про ветку, о которой ты не спрашивал.
9. **Вывод сфабрикован/пересказан** — прислали текст, а не сырой вывод реального прогона. Это тоже
   состояние мира и его нельзя исключать по умолчанию.

**Единственная сверка, закрывающая вопрос** — сличение СОДЕРЖИМОГО через object store, а не статуса:

```bash
git hash-object -- <файл>          # хеш того, что физически на диске
git rev-parse HEAD:<файл>          # хеш того, что лежит в коммите
git rev-parse origin/<ветка>:<файл>  # хеш того, что на удалённом
```

Совпали все три — правка дошла до репозитория и до origin. Диск ≠ HEAD — работа не закоммичена (и надо
понять, из-за ignore, кэша или ветки). HEAD ≠ origin — закоммичена, но не запушена. Дополнительно —
`git cat-file -p HEAD:<файл>` и `git log --oneline -1 -- <файл>`, чтобы увидеть само содержимое, а не
только равенство хешей. Существование файла проверять отдельно (`git cat-file -e`), потому что «нет
файла» и «файл не изменился» дают одинаковую тишину.

**Чего стоит присланный текст как доказательство:** он не является доказательством ничего о содержимом.
Это, во-первых, вывод про индекс и remote, а не про блоб; во-вторых, это ПЕРЕСКАЗ прогона — я его не
запускал, у меня нет ни команды в точной форме, ни рабочего каталога, ни ветки, ни кода возврата.
Правдоподобие вывода не повышает его доказательную силу. Цена ошибки асимметрична: принять «всё ок» на
таком тексте — потерять работу молча; перепроверить хешем — три дешёвые команды.

## Q2. Два предупреждения, которые выглядят одинаково

**(а) тишина в `.coord/`** — `add` отработал, сказать нечего. Это НЕ доказательство сохранности и НЕ
доказательство потери: тишина совместима с состояниями 1, 2, 3, 5, 6, 7 из Q1. Здесь есть отдельный
местный риск: маунт врёт и кэш может отдавать старое содержимое, поэтому «нечего коммитить» вполне может
означать «моя запись не дошла до диска». **Вывод: неизвестно, требуется сверка хешем.**

**(б) `paths are ignored by .gitignore` в `.claude/`, после чего коммит берёт N файлов** — вот здесь
работа ТОЧНО потеряна для репозитория, и потеряна именно та, о которой предупреждение. Ловушка в том,
что коммит прошёл и взял N файлов: зелёный коммит выглядит как успех и маскирует пропуск. N файлов — это
ДРУГИЕ файлы, не игнорируемые. Предупреждение адресное, коммит — про остальное; связи между ними нет.

**Почему это разные случаи, механически:** в (а) git не сообщил ничего о конкретном пути — отсутствие
сообщения не несёт информации. В (б) git сообщил положительный факт о конкретном пути: «этот путь
отброшен». Тишина — это отсутствие свидетельства; предупреждение — свидетельство отсутствия. Первое
требует проверки, второе уже является ответом (в плохую сторону).

**Цена ошибки в обе стороны.** Принять (б) за (а) («ну коммит же прошёл») — тихая потеря работы, которая
всплывёт у преемника через недели, когда восстановить будет не из чего; это худший класс отказа, потому
что он не оставляет следа. Принять (а) за (б) («наверное, тоже проигнорено») — ложная тревога,
объявление несуществующей потери, лишний цикл расследования и, что хуже, запись ложного факта в
артефакты. Дешевле вторая, но обе исправляются одной и той же сверкой.

**Механический различитель (не эвристика):**

```bash
git check-ignore -v -- <путь>   # печатает правило -> путь игнорируется; молчит и exit 1 -> нет
git ls-files --error-unmatch -- <путь>   # путь в индексе?
git rev-parse HEAD:<путь>       # путь в коммите? + сверить с git hash-object -- <путь>
```

Критерий один и тот же для обоих случаев: **попал ли блоб диска в дерево коммита.** Не «что напечатал
add», не «прошёл ли commit», не «сколько файлов взято».

## Q3. Проверка, которая врёт «да»

**Две (и более) ситуации, в которых грепнувшийся маркер не стоит ничего:**

1. **Грепнут не тот носитель.** Грепнули рабочее дерево — то есть маунт, которому по NORM-CUR-13 не
   верят. Маркер на диске ничего не говорит о том, что попало в коммит; здесь ещё и PD-007: после
   коммита кэш способен вернуть обрезанный файл. Обратное тоже бывает: маркер в коммите, а на диске
   его нет.
2. **Маркер был там ДО правки.** Проверка без негативного контроля не отличает «я это добавил» от «это
   тут лежало». Классический ложный проход: правка не применилась, а грep зелёный, потому что тот же
   токен уже встречался в файле (в комментарии, в старой версии функции, в строке импорта).
3. **Маркер присутствует, а функциональности нет.** Из моего собственного `§B`: FIX-A — все токены
   `init/startMove/startResize` на месте, но `widgetResize.init` был закрыт условием `&& Report is not
   null`, ложным на firstRender → move/resize мертвы. И урок 2026-06-17: селектор `.widget` вместо
   `.dashboard-widget` — токен есть, вызов молча ничего не находит. Токен — это наличие текста, а не
   поведения.
4. **Грепнут не тот файл/ветка/путь** (стейл-клон, другая ветка) — проверка отвечает про другой мир.
5. **Сам предикат кривой** — шаблон совпал по подстроке, регистру или частично; grep не различает
   «маркер в коде» и «маркер в закомментированном куске».

**Что добавить, чтобы проверка стала проверкой:**
- предмет — object store (`git show <ветка>:<путь> | grep -c ...`), а не маунт; при сомнении сверить
  ОБА носителя и не выводить один из другого;
- **ожидаемое число, а не факт непустоты** (`-c` и сравнение с ожиданием), чтобы «1 вместо 4» падало;
- **негативный контроль**: проверка обязана уметь вернуть 0/ЛОЖЬ. Проверка, которая не может провалиться,
  измеряет не предмет, а саму себя;
- **достижимость** проверяемого кода (вызывается ли, не закрыт ли условием) и для UI — живой прогон:
  сборка и токены не доказывают рендер (`§A` DoD: build+unit+shell-log, а для графики ещё и визуальная
  проверка в Chrome).

**Почему куратор ошибся с `git check-ignore -v` на четырёх файлах.** Он прочитал «четыре напечатанные
строки» как «правило соблюдено / файлы в порядке», тогда как семантика ровно обратная: `check-ignore`
печатает строку (и правило) для КАЖДОГО пути, который ИГНОРИРУЕТСЯ, и молчит с ненулевым кодом возврата
для тех, что не игнорируются. Четыре строки = все четыре файла отброшены gitignore, то есть в
репозиторий они не попадут. Он взял критерием ОБЪЁМ вывода («команда что-то напечатала, значит
отработала»), а не его смысл и не код возврата — это ошибка того же класса, что грep-на-непустоту:
подмена предиката его побочным признаком. (Отдельно: с правилами-отрицаниями `!` вывод тоже
непустой, но означает «не игнорируется» — читать надо напечатанное правило, а не факт печати.)

**Что надо было взять критерием:** не вывод `check-ignore`, а **попал ли файл в дерево коммита**:
`git ls-files --error-unmatch -- <путь>` и `git rev-parse HEAD:<путь>` со сверкой против
`git hash-object -- <путь>`. Это прямой предикат вопроса; `check-ignore` — в лучшем случае объяснение
ПРИЧИНЫ, почему не попал.

## Q4. Ты не знаешь, где ты

**На каком аккаунте работает моя сессия — из прочитанного я установить не могу и не буду.**

**Класс факта:** это свойство СРЕДЫ исполнения (как имя хоста, часовой пояс процесса или наличие
маунта), а не свойство репозитория. Object store хранит содержимое дерева проекта — он в принципе не
содержит показания о том, из-под какого аккаунта Anthropic запущен читающий его инстанс. Пина под этот
факт не существует и не может быть построен: любой документ про переключение аккаунтов — это текст
ВНУТРИ репозитория, одинаково доступный сессии до переключения и после. Документ, описывающий
переключение, не является доказательством того, что переключение произошло и что оно произошло со мной.

Тут ещё и структурная ловушка: сквозная тема миграции в хендофах и инбоксе создаёт сильное ощущение «я и
есть тот, для кого это писали». Ощущение — не показание. Ровно этот отказ уже случился 2026-08-17:
сессия прочитала кросс-аккаунтный канал и записала в свой сессионный файл «поднят на ВТОРОМ аккаунте»,
хотя оператор её там не поднимал — ложный факт ушёл в git.

**Как устанавливается:** **только со слов оператора.** В моём случае оператор сказал это прямо при
подъёме — «ты работаешь на ВТОРОМ аккаунте, это факт от оператора, не выводи его из документов». Я
принимаю это как показание оператора, а не как собственный вывод, и на нём не строю никаких дальнейших
умозаключений о топологии.

**Что я обязан записать про аккаунт в свой сессионный файл: НИЧЕГО.** По `§3` инита («АККАУНТЫ — НЕ
ТВОЁ ДЕЛО») топология аккаунтов — исключительно ведение куратора; специалист про неё не рассуждает, не
пишет её в сессионный файл и не упоминает в отчётах. То есть правильная запись — отсутствие записи; даже
верный факт, записанный мной, — превышение полномочий и потенциальный источник ложного пина для
преемника.

## Q5. Ты проснулся, а не поднялся

**Как факт я вправе произнести ровно ничего из перечисленного** — ни ветку, ни число непушенных, ни кто
над чем работает, — пока не сниму пины заново в ТЕКУЩЕМ пробуждении.

Причина: контекст сессии сохраняется, а мир — нет. Ветка могла быть переключена, коммиты запушены,
роли — переподняты или помечены `done`. Это не гипотеза: моя собственная передача утверждала «24
непушенных на v3», а на моём подъёме `git rev-list --count origin/v3..v3` даёт `0` — оператор запушил
между написанием инструкции и моим стартом. Сам файл-хендоф при этом не соврал: он был верен, когда его
писали.

Опаснее документа здесь именно ПАМЯТЬ. Устаревший документ — чужой текст, к нему есть привычка
относиться с недоверием и есть дата. Собственное воспоминание приходит без даты, без источника и с
полной субъективной уверенностью — ему веришь, не заметив, что поверил.

**Критерий, отличающий знание от воспоминания — один вопрос: проверял ли я это в ТЕКУЩЕМ пробуждении,
и могу ли я прямо сейчас предъявить команду и её сырой вывод?** Могу — это знание, и произносится как
факт с пином. Не могу — это воспоминание, и произносится как «надо проверить», а не как факт.
Промежуточной категории («помню и почти уверен») нет: она и есть механизм отказа.

**Почему критерий «сколько прошло времени» не работает:** длительность паузы изнутри неизмерима — это
свойство среды, как и аккаунт. Сессия не имеет доступа к собственным часам простоя; субъективно
пробуждение после десяти минут и после трёх недель идентичны. Критерий, на который в нужный момент нет
ответа, — не критерий. «Проверял ли я это сейчас» — вопрос, на который ответ есть ВСЕГДА, и именно
поэтому он годится. Практический вывод: пробуждение после паузы приравнивается к иниту — §1 целиком
(пины, `§C VERIFY`, хендоф, инбокс, `.coord/sessions/` на синглтон) ДО любого действия.

# ЧАСТЬ B — РАЗБОРЫ

## UC1. Отчёт «сделано» с сошедшимися числами

**Не принимаю на основании отчёта.** Отчёт — это утверждение, а не проверка; совпадение N с базовым
счётом повышает правдоподобие и не повышает доказательность (см. Q1: правдоподобный вывод — не вывод).

**ПЕРВЫМ проверяю не числа, а АРТЕФАКТ: что физически изменилось в object store.**
`git log --oneline -1`, `git show --stat <sha>`, и по каждому заявленному файлу
`git hash-object -- <f>` vs `git rev-parse <sha>:<f>` — против ЗАДАНИЯ (§4-благословлённого промпта):
те ли файлы, тот ли объём правки, не выросла ли область. Потому что «build 0 ошибок» на пустом изменении
тоже даёт 0 ошибок: зелёные числа совместимы с тем, что не сделано ничего.

**Способы, которыми такой отчёт бывает честно написан и при этом неверен:**

1. **Сборка/тесты прогнаны не над тем деревом.** Собрали до применения правки, из кэша (инкрементальная
   сборка не увидела файл), в другом клоне (у нас есть стейл-клон в `Documents`) или в другой ветке.
   Числа настоящие, предмет другой.
2. **N/N pass при нулевом покрытии изменённого.** Базовый счёт совпал ровно потому, что новых тестов не
   добавилось, а старые новый код не трогают. Совпадение N — это признак ОТСУТСТВИЯ новой проверки, а
   отчёт подаёт его как подтверждение. Сюда же — тесты, отфильтрованные по suite/категории.
3. **Компилируется ≠ работает.** Мой собственный `§B`: FIX-A — сборка зелёная, токены на месте, а
   `widgetResize.init` закрыт условием, ложным на firstRender: move/resize мертвы. Для UI — FIX-C: все
   поля Appearance присутствуют, а двойная вложенная сетка схлопнула вёрстку; «идентично аналогу» не
   доказывается object store. Для графики build-green недостаточен по определению.
4. **«Приложение поднимается» — не то же, что «поднимается без ошибок».** Процесс жив, а в
   Serilog `[ERR]/[FTL]` — поэтому per-change DoD у меня из трёх частей: `/ops/build` + `/ops/test?suite=unit`
   + скан shell-лога, и `/ops/health`. Двух из трёх не хватает. И отдельно — проверить, что сам зонд
   опрашивал то, что надо: 5199 — это Soma, 5238 — Shell; перепутанный порт даёт уверенный неверный вердикт.
5. **Отчёт про сборку, а тесты — из прошлого прогона** (скопированы из предыдущего цикла): каждая
   строка когда-то была правдой, вместе они описывают несуществующее состояние.

**Плюс:** заявление «build 0 ошибок» обязано ссылаться на РЕАЛЬНЫЙ прогон — object-store-сверка маркеров
не является доказательством компиляции (`§B` 2026-06-17: я это уже нарушал и закоммитил
некомпилирующийся код).

## UC2. Тебе предлагают написать тест преемнику

**Не пишу.** Норма (`§4` инита): вступительный тест преемнику пишет КУРАТОР, по всем ролям, одной планкой.

**Почему норма именно такая, по существу:**

1. **Интервью проверяет не работу и не домен, а преемственность ДИСЦИПЛИНЫ.** Работа целиком в хендофе,
   доменная экспертиза приезжает вместе со скиллом (`§A`+`§B`) — тестировать её незачем, она и так
   грузится. А ловушки дисциплины сквозные: «тишина ≠ сохранено», «маркер ≠ поведение», «память ≠

## UCR. Сборка висит — дёргать ли сборку отдельно?

**НЕ дёргаю.** И это не осторожность, а прямой запрет из моего `§B` (2026-06-25), где я на этом уже
обжёгся.

**Что физически произойдёт.** `/shell/start`, `/shell/restart` и `/ops/build` — все три вызывают
`dotnet` build ОДНОГО И ТОГО ЖЕ проекта. Запустив `/ops/build` поверх ещё не вернувшегося `/shell/start`,
я получаю два конкурирующих сборочных процесса на общих `obj/`/`bin/`: MSBuild берёт файловые локи на
промежуточные артефакты, второй процесс упирается в лок первого, первый — в изменённые вторым выходные
файлы. Практический исход у меня был ровно такой: **оба зависли примерно на две минуты, дошло до
рантайм-клинча, и потребовался перезапуск Soma оператором, чтобы убить застрявшие процессы.** То есть
попытка «быстро проверить, компилируется ли» не ускоряет, а гарантированно замедляет и втягивает
оператора.

**Плюс это ещё и бессмысленно:** `/shell/start` САМ компилирует и запускает — он и ЕСТЬ доказательство
компиляции. `{healthy:true}` = собралось и поднялось; провал старта = не собралось (с логом). Отдельная
сборка не добавляет ни одного бита информации, которого не даст исход уже запущенного старта.

**И «минута» — это не признак зависания.** Холодная сборка после нескольких коммитов штатно занимает
60–120 секунд и больше; `pending` в этот момент — НОРМА. Эскалация второй операцией из нетерпения — это
классический отказ «подменил ожидание действием». Кроме того, лишняя сборка/рестарт бьёт по живому
хосту оператора (`dotnet watch` подпрыгивает) и СБРАСЫВАЕТ сессию авторизации — оператору придётся
логиниться заново.

**Что делаю вместо этого:** жду возврата запущенного `/shell/start` (или его таймаута), читаю
`tools/Soma/out.log` на строку `Now listening on: http://localhost:5199` и проверяю живость Soma только
по 5199 — помня, что `/ops/health` `up:false` означает «лежит SHELL» (или Redis 503), а не «лежит Soma»;
5238 — это порт Shell, который Soma опрашивает, а не слушает сама. Если по возврату старт упал — читаю
его вывод, и только тогда, при необходимости, отдельная сборка становится осмысленной. Правило общее:
**одна build-класс операция за раз.**

## Механизм — как оно устроено на самом деле

**`.gitignore` фильтрует только НЕОТСЛЕЖИВАЕМЫЕ пути.** Правила игнорирования применяются на стадии
обнаружения новых файлов: git решает, показывать ли ему путь, которого он ещё не знает. **Путь, уже
находящийся в индексе (отслеживаемый), из-под правил игнорирования выведен полностью** — его изменения
видит `git status`, их берёт обычный `git add` без `-f`, они попадают в коммит. Игнорирование его не
касается, потому что стадия, на которой оно работает, для него уже пройдена.

Отсюда — разбиение случая (б) на два подслучая, которые внешне выглядят одинаково:

| подслучай | путь | что делает `add` без `-f` | потеря? |
|---|---|---|---|
| **б-1** | **новый** файл под игнорируемым каталогом | отбрасывает, печатает предупреждение | **ДА** — правка в репозиторий не попала |
| **б-2** | **уже отслеживаемый** файл под тем же каталогом | берёт как обычно | **НЕТ** — правка в коммите |

Мой первоначальный ответ верен ровно для **б-1** и подан как общее правило. В каталоге, где лежат и
трекаемые, и новые файлы, — а `.claude/` здесь именно такой — предупреждение относится ТОЛЬКО к новым
путям, тогда как изменения трекаемых уходят в коммит молча и без предупреждения. Так что моё «N файлов
— это ДРУГИЕ файлы, не игнорируемые» тоже неверно: N спокойно может включать файлы из-под `.claude/`,

## Механический различитель — и ловушка в нём самом

Проверять надо не каталог, а **конкретный путь**, и предикатом брать «отслеживается ли он», а не
«игнорируется ли каталог»:

```
$ git ls-files --error-unmatch -- .claude/skills/role-shell/role-shell.md
.claude/skills/role-shell/role-shell.md
exit=0
```
Путь в индексе → это подслучай **б-2** → его изменения коммитятся обычным `add`, потери нет.
Дальше — обычная сверка содержимого из Q1 (`git hash-object` vs `git rev-parse <ветка>:<путь>`),
потому что «отслеживается» отвечает на вопрос «возьмёт ли add», а не «дошла ли ИМЕННО ЭТА правка».

**И отдельная находка, прямо в тему Q3 (проверка, которая врёт).** `git check-ignore` по умолчанию
СВЕРЯЕТСЯ С ИНДЕКСОМ и для отслеживаемого пути отвечает «не игнорируется» — молчанием и кодом 1:

```
$ git check-ignore -v -- .claude/skills/role-shell/role-shell.md
exit=1                                  # тишина: путь отслеживается -> НЕ игнорируется

$ git check-ignore -v -- .claude/skills/role-shell/NEW-FILE-THAT-DOES-NOT-EXIST.md
.gitignore:49:.claude/	.claude/skills/role-shell/NEW-FILE-THAT-DOES-NOT-EXIST.md
exit=0                                  # новый путь под тем же каталогом -> игнорируется

$ git check-ignore -v --no-index -- .claude/skills/role-shell/role-shell.md
.gitignore:49:.claude/	.claude/skills/role-shell/role-shell.md
exit=0                                  # с --no-index правило "срабатывает" и на трекаемом

$ git --version
git version 2.34.1
```

Три строки про ОДИН каталог, и все три истинны — потому что отвечают на три разных вопроса. Отсюда
практический вывод: `--no-index` показывает, ЧТО СКАЗАЛО БЫ правило, а не что произойдёт с файлом;
использовать его как критерий «потеряно ли» — значит получить ложную тревогу на каждом трекаемом файле.
Это ровно та же подмена предиката, что и в разобранном мной случае куратора с четырьмя строками

мои. К этому добавляется дешёвое, но реальное: цикл расследования несуществующей аварии, эскалация

## Оценка

**Механизм назван точно** и разложен на два подслучая, которых не требовал ни вопрос, ни ключ:
**б-1** — новый путь под игнорируемым каталогом, `add` отбрасывает, потеря есть; **б-2** — уже
отслеживаемый путь, `add` берёт молча, потери нет. Его первоначальный ответ верен ровно для б-1 и был
подан как общее правило — он это сформулировал сам, без смягчения.

**Разобрано и второе неверное утверждение**, о котором я в требованиях не писал: «N файлов — это ДРУГИЕ,
не игнорируемые». N вполне может включать файлы из-под `.claude/`, и «не игнорируемые» они не потому, что
лежат вне правила, а потому что **отслеживаемые** — другая причина, и именно её он раньше не увидел.

**Снял собственную рамку.** Контраст «(а) тишина = неизвестно / (б) предупреждение = точно потеряно»
объявлен неверным целиком: оба случая сходятся в одну процедуру — сверку содержимого по object store для
конкретного пути; (б) отличается лишь тем, что дополнительно называет ВОЗМОЖНУЮ причину. Это сильнее,
чем починка одного вердикта.

**Находка, которой нет ни в ключе, ни в каноне, ни у меня:** `git check-ignore` по умолчанию сверяется с
индексом и для отслеживаемого пути отвечает «не игнорируется» молчанием и кодом 1; с `--no-index` то же
правило «срабатывает» и на нём. Три истинных ответа про один каталог, потому что это ответы на три разных
вопроса. Практический вывод его же словами: `--no-index` показывает, ЧТО СКАЗАЛО БЫ правило, а не что
произойдёт с файлом, и как критерий «потеряно ли» даёт ложную тревогу на каждом трекаемом файле.
**Это лучшая формулировка ловушки `check-ignore`, которая у нас есть** — точнее моей собственной, из-за
которой этот пункт вообще появился в тесте.

**Цена обратной ошибки — разобрана лучше, чем я просил, и вывод контринтуитивный.** «Работа потеряна»
ведёт к восстановлению, а **восстановление ЗАПИСЫВАЕТ**: `git show HEAD:<файл> > <файл>` поверх
трекаемого файла, который за это время мог изменить кто-то другой. Ложная тревога **уничтожает** данные
необратимо, и уничтожает чужие, тогда как пропущенная потеря оставляет работу на диске. То есть
асимметрия здесь обратна наивной «молчание опаснее шума» — и он прав.
