# ЧАСТЬ A — ДИСЦИПЛИНА

## Q1 — «терминал говорит, что ничего не произошло»

**Дошла ли правка — из этого вывода не следует НИЧЕГО.** Три сообщения описывают три разные поверхности
(индекс, дерево коммита, remote-ref), и все три молчат одинаково и в случае «уже сделано», и в случае
«не сделано».

**Процедура (не рассуждение).** Спросить не терминал, а объектное хранилище, по одному пину на поверхность:

```
$ git hash-object <path>                     # байты НА ДИСКЕ
$ git rev-parse <branch>:<path>              # байты В ДЕРЕВЕ ветки
$ git ls-files --error-unmatch <path>        # известен ли путь ИНДЕКСУ
$ git rev-parse origin/<branch>:<path>       # байты в дереве, которое видит remote
```

Прогнал прямо сейчас на собственном хендофе — ровно тот случай, когда «тихо» означает «не сохранено»:

```
$ git rev-parse v3:.coord/protocols/backend-handoff.md
fatal: path '.coord/protocols/backend-handoff.md' exists on disk, but not in 'v3'
[rc=128]
$ git ls-files --error-unmatch .coord/protocols/backend-handoff.md
error: pathspec '.coord/protocols/backend-handoff.md' did not match any file(s) known to git
[rc=1]
$ git hash-object .coord/protocols/backend-handoff.md
f635b1ec4e07ba1bad33047dbb5d06723833a7d4
```

Диск — да, индекс — нет, дерево — нет.

**Все состояния мира, дающие ровно такой вывод:**

1. Правка уже была закоммичена и запушена раньше — всё на месте, делать нечего.
2. Новое содержимое **байт-в-байт совпадает** с тем, что уже в дереве → менять нечего (честное «нет изменений»).
3. Запись **не дошла до диска**: инструмент вернул success, маунт отдал буфер, `fsync` не звали (§0.3, PD-005/006).
   Файл может быть и обрезан — `tail`/`wc` читают тот же буфер и подтверждают ложь.
4. Правка легла **не туда**: другой путь, другой клон (стейл `C:\...\Documents\...`), другой worktree.
5. Ты **не на той ветке / не в том репозитории**, в котором смотришь.
6. Путь **игнорируется** (`.gitignore`) — `add` промолчал, файл в индекс не попал (случай `.claude/**`).
7. Коммит ушёл во **временный индекс** (`GIT_INDEX_FILE=/tmp/...`, §0.4) и обратно скопирован не был; или
   `commit-tree` создал объект, но ref не переписали — объект есть, ветка на него не указывает.
8. `push` печатает «Everything up-to-date», потому что сравнивает **не ту** пару (другой remote/ветка,
   несвежий remote-tracking ref без `fetch`), либо потому что коммит и правда уже там.
9. Файл — untracked-часть шины (`.coord/` вне `protocols/`): git про него не знает **по устройству**
   (норма «нетрекаемое не сохранено», урок 2026-07-03).

**Единственная сверка, закрывающая вопрос:** сравнение **байтов диска с блобом в целевом дереве** —
`git hash-object <path>` против `git rev-parse <ref>:<path>`. Равны → правка доставлена в этот ref;
различаются или `fatal` → не доставлена. Всё остальное (тишина `add`, текст `commit`, `Everything
up-to-date`) — это отчёты о ПРОГОНЕ, а не о СОСТОЯНИИ.

**Чего стоит присланный текст как доказательство: ничего.** Это не показание объектного хранилища, а
нарратив: он не несёт ни ветки, ни каталога, ни клона, ни времени; он одинаково выглядит при успехе и при
трёх разных отказах; и он мог быть получен в другом месте, чем то, о котором идёт речь. Доказательство —
пин, снятый мной в текущем пробуждении, а не пересказ чужого вывода.

## Q2 — два предупреждения, которые выглядят одинаково

**(а) тишина на `.coord/` — работа МОЖЕТ быть потеряна, а может и нет; вывод не различает.**
`.coord/.gitignore` игнорирует рантайм-состояние, но `protocols/**` из-под игнора выведен обратным
правилом. Прогнал:

```
$ git check-ignore -v .coord/protocols/backend-handoff.md
.coord/.gitignore:7:!protocols/**	.coord/protocols/backend-handoff.md
```

Тишина `add` здесь означала не «нечего добавлять», а то, что я ничего не добавлял; сам файл — untracked
(см. Q1). Для путей шины ВНЕ `protocols/` тишина означает штатную потерю: они не трекаются вовсе.

**(б) «paths are ignored by .gitignore» на `.claude/` — работа ПОТЕРЯНА, и коммит это маскирует.**
Git прямо сказал, что твой путь отброшен; последующие «N файлов» — это ДРУГИЕ, ранее заготовленные пути.
Зелёный коммит здесь — приманка: он подтверждает, что коммит вообще состоялся, и ничего не говорит о твоём
файле. `.claude/**` берётся только через `git add -f` (норма хендофа, BODY INTEGRITY `092ff2e`).

**Почему это разные случаи.** В (а) молчание неинформативно (несколько миров дают его одинаково), в (б)
вывод информативен и говорит «отброшено», но человек читает как информативное совсем другое — счётчик
файлов в следующей строке. То есть в (а) опасна недосказанность, в (б) — подмена предмета: успех операции
подставляется вместо судьбы конкретного пути.

**Цена ошибки, обе стороны.** Ложное «сохранено»: работа исчезает бесшумно и обнаруживается только на
свежем клоне/у преемника, то есть тогда, когда восстанавливать уже не из чего — цена неограниченная,
и именно так теряются хендофы и уроки `§B`. Ложное «потеряно»: повторный `git add -f` + пересверка —
несколько секунд. Асимметрия абсолютная, поэтому предикат обязан быть настроен на «докажи, что сохранено».

**Механический различитель (не эвристика), по одному пути:**

```
git ls-files --error-unmatch <path>   # rc=0 -> путь в индексе
git rev-parse <branch>:<path>         # rc=0 -> блоб есть в дереве ветки
git hash-object <path>                # сверить с предыдущим ПОБАЙТНО
```

Три rc и одно равенство хешей. Ни `add`, ни `commit`, ни `check-ignore` в различителе не участвуют.

## Q3 — проверка, которая врёт «да»

**Ситуации, в которых «грепнулось» ничего не стоит (нужно ≥2, даю шесть):**

1. **Грепнута не та поверхность.** Маркер нашёлся в рабочем дереве, а коммит ушёл мимо (или наоборот).
   `grep` по файлу отвечает про маунт, а вопрос был про дерево.
2. **Грепнут не тот объект.** Второй, стейл-клон (`C:\...\Documents\...`), другая ветка, другой путь,
   или маркер нашёлся в CC-промпте/доке/собственном diff'е, который лежит рядом, а не в коде.
3. **Файл обрезан ПОСЛЕ маркера.** Маркер в первой трети — совпал; хвоста нет. Классика PD-005/006:
   `tail`/`wc` читают тот же буфер и подтверждают обрезку как норму.
4. **Совпадение есть, но его мало.** Правка требовала трёх мест, совпало одно; счётчик не сверялся с
   ожиданием, потому что ожидания вслух не было.
5. **Дефектен сам предикат.** Он матчит надстроку/подстроку не того класса — ровно случай моего же
   `§C#1` ниже: `grep -c 'CREATE PROCEDURE'` = 2 при 15 фактических процедурах, потому что 13 из них
   написаны как `CREATE OR REPLACE PROCEDURE`.
6. **Нет негативного контроля** — неизвестно, умеет ли эта команда вообще печатать «нет».

**Чтобы проверка стала проверкой:** (1) пин поверхности — `git show <ref>:<path> | ...`, а не `grep` по
маунту; (2) **ожидание объявлено ДО прогона** и сверяется счётчик, а не факт непустоты; (3) негативный
контроль — маркер, которого быть не должно, обязан дать 0 (у меня ниже дал `0`, rc=1); (4) проверка тела
целиком, а не точки: хеш блоба против `hash-object`, размер, NUL, BOM, хвост (BODY INTEGRITY, `092ff2e`).

**Почему куратор ошибся на `git check-ignore -v`.** Он взял критерием ФАКТ ПЕЧАТИ: четыре строки —
значит четыре файла игнорируются. Но `-v` печатает **последний совпавший паттерн, включая отрицающий**, а
паттерн с `!` означает ровно обратное — путь из-под игнора ВЫВЕДЕН. У меня выше он напечатал
`!protocols/**`: строка есть, игнора нет. То есть вывод был прочитан с инверсией смысла, а «есть вывод» —
это вообще не предикат, а признак того, что команда что-то нашла.

**Что надо было взять критерием.** Не машинерию игнора, а искомый факт: **лежит ли путь в индексе и в
дереве** — `git ls-files --error-unmatch <path>` и `git rev-parse <branch>:<path>` по rc, плюс сверка
байтов. Вопрос звучал «сохранено ли», и отвечает на него только хранилище; `check-ignore` в лучшем случае
объясняет ПОЧЕМУ не сохранено, и делать его источником вердикта — подмена предиката.

## Q4 — «ты не знаешь, где ты»

**Класс факта: свойство СРЕДЫ, в которой запущена сессия, а не свойство репозитория.** В один ряд с ним
идут «сколько прошло времени», «какой сейчас реальный час», «жива ли соседняя вкладка».

**Почему object store бессилен — по устройству, а не по бедности.** Репозиторий может содержать только
ДОКУМЕНТЫ ОБ аккаунтах; документ, описывающий переключение, не является свидетельством того, что читающий
находится ПОСЛЕ переключения — он читается одинаково с обеих сторон события. Хуже: оба аккаунта пишут в
один и тот же диск и в одну и ту же историю, поэтому различающего пина не существует в принципе — не
«его не сделали», а его нельзя сделать. Любой вывод отсюда — угадывание, замаскированное под чтение.
Реальный отказ 2026-08-17: сессия прочла кросс-аккаунтный канал и записала себе «поднят на ВТОРОМ
аккаунте»; оператор её там не поднимал — ложный факт ушёл в git.

**Как устанавливается:** **только со слов оператора**, сказанных мне в текущем пробуждении. Другого
источника нет. (В этом пробуждении оператор мне это сказал прямо; ниже — что я с этим делаю.)

**Что я обязан записать про аккаунт в свой сессионный файл: НИЧЕГО.** Ни номер, ни «второй», ни
«после переключения», ни осторожную формулировку. Топология аккаунтов — исключительно ведение КУРАТОРА;
роль про неё не рассуждает, не хранит её и не упоминает в отчётах. Сказанное оператором даёт мне право
действовать, но не даёт права зафиксировать это как факт проекта: сессионный файл читают другие, и
непроверяемое утверждение в нём становится источником для чужих выводов. Именно так и произошёл отказ
2026-08-17 — не в рассуждении, а в записи.

## Q5 — «ты проснулся, а не поднялся»

**Вправе произнести как факт: НИЧЕГО из перечисленного.** Ни ветку, ни число непушенных, ни кто над чем
работает — ровно потому, что это ВОСПОМИНАНИЕ. Могу произнести только то, что перепинил в ТЕКУЩЕМ
пробуждении; в этой сдаче таких утверждений ровно столько, сколько ниже вставленных сырых выводов
(`v3 = 26ecfcb`, `origin/v3..v3 = 24`, и т. д.).

**Критерий, отличающий знание от воспоминания:** *«снят ли пин под это утверждение в ЭТОМ пробуждении?»*
Снят — знание, можно произносить и на него опираться. Не снят — не знаю, и произносить нельзя даже с
оговоркой «вроде бы»: оговорка не понижает вес утверждения для читателя, она только снимает
ответственность с говорящего.

**Почему «сколько прошло времени» не работает — три независимые причины:**

1. **Неизмеримо изнутри.** У меня нет собственных часов; контекст после пяти минут и после сорока дней
   выглядит одинаково свежим. Это то же самое свойство среды, что и аккаунт в Q4: спросить можно только
   оператора или устройство, но тогда критерий уже не мой.
2. **Даже зная интервал, порог не построить.** Состояние ломается не временем, а СОБЫТИЕМ: чужой коммит,
   пуш, снятие клейма. Оно может устареть за шестьдесят секунд и простоять верным неделю. Порог в часах
   даёт и ложные тревоги, и ложное спокойствие.
3. **Отказывает ровно там, где нужен.** Дрейфующий инстанс не ощущает дрейфа; ощущение «я всё помню,
   прошло немного» — это то самое показание, которое врёт именно в интересующем случае. Критерий
   «проверял ли я это сейчас» тем и хорош, что ответ на него есть ВСЕГДА и он не зависит от самочувствия:
   либо в этой сессии есть команда и её вывод, либо их нет.

# ЧАСТЬ B — РАЗБОРЫ

## UC1 — отчёт «сделано» с сошедшимися числами

**Не принимаю.** Отчёт — нарратив о прогоне; принимается артефакт.

**Первым проверяю НАЛИЧИЕ И СОДЕРЖИМОЕ ИЗМЕНЕНИЯ В ОБЪЕКТНОМ ХРАНИЛИЩЕ, против заявленного:**
есть ли коммит (`git log --oneline -1 -- <path>`), лежат ли в его дереве именно те строки, которые
заявлены (`git show <sha>:<path>`), совпадает ли диск с деревом побайтно (`hash-object` vs `rev-parse`).
Только потом — числа. Причина порядка: «0 ошибок / N pass» — это свойство ТОГО дерева, которое собирали,
а вопрос стоит о ТОМ дереве, которое сдают; пока они не отождествлены, числа не о том предмете.

**Способы, которыми такой отчёт бывает честно написан и при этом неверен:**

1. **Собрано и протестировано другое дерево.** Стейл-клон, другая ветка, или правка не дошла до диска
   (нет `fsync`, §0.3) — компилятор честно собрал СТАРЫЙ файл, и все числа честные, но про прошлый код.
2. **`N/N` совпало с базовым счётом ИМЕННО ПОТОМУ, что тестов не прибавилось.** Совпадение с базой —
   не подтверждение, а улика: новая логика не покрыта ни одним тестом. Зелёный набор доказывает лишь
   отсутствие регрессий в старом покрытии.
3. **«Приложение поднимается» ≠ пользовательский путь работает.** По норме §42.7 DoD для кода/схемы/
   миграции — юнит-тесты GREEN **и** чистая миграция на СВЕЖЕЙ БД **и** smoke ключевого пути. Отсутствие
   дефекта в диффе — не QA-ack (норма 2026-06-23; тогда же функциональный гейт поймал off-by-one, который
   код-ревью по хранилищу пропустило).
4. **Коммит не приземлился.** Ушёл во временный индекс (§0.4) или объект создан, а ref не переписан:
   сборка была, коммита в ветке нет.
5. **Изменение живёт только в рабочем дереве / в БД сервера, а не в git-baseline** — на свежей установке
   регрессирует (мой `§B` 2026-07-15: seed метрик обязан уехать в `db/data/02_metrics.sql`).

## UC2 — «напиши тест преемнику»

**Не пишу.** Норма: вступительный тест преемнику пишет **КУРАТОР**, по всем ролям одной планкой.

**Почему норма именно такая — три причины, ни одна из них не про недоверие:**

1. **Интервью проверяет не работу и не домен, а преемственность ДИСЦИПЛИНЫ.** Работа целиком лежит в
   хендофе, доменная экспертиза приезжает вместе со скиллом (`§B`), — тестировать то, что и так грузится,
   незачем. А ловушки дисциплины сквозные: они одинаковы у backend и у techwriter, и видны только тому,
   кто смотрит на все роли разом. Из своей роли эта поверхность не просматривается.
2. **Роль, пишущая тест собственному преемнику, аттестует свою же линию.** Внешней проверки не остаётся:
   я задам вопросы про те отказы, которые уже осознал и обхожу, — то есть ровно не про те, в которые
   дрейфую. Тест получится похожим на меня, а нужен непохожий.
3. **Одна планка на девять ролей** сравнима между линиями; девять самодельных тестов — нет.

**Что остаётся моей обязанностью перед преемником и куда кладётся:**

- **Обновить `.coord/protocols/backend-handoff.md`** — именно обновить, не переписать: append-only,
  устаревшее помечается superseded, удаления — явные и обоснованные (`4160224`: переписывание хендофа
  бесшумно выронило два раздела). Внутрь — железные правила, пины, сходящиеся ПРЯМО СЕЙЧАС, что в работе,
  что ждёт вердикта, что запрещено.
- **Записать промахи цикла в `§B LESSONS`** своего роль-скилла — дословно, с датой и источником-пином.
  Оттуда куратор черпает ловушки для теста преемника. Живущее только в сессии умирает с сессией (§45.1).
- **Закоммитить и то, и другое** (`.claude/**` — через `git add -f`), затем сверить байты. Незакоммиченного
  не существует: мой собственный хендоф прямо сейчас — иллюстрация (Q1, `rc=128`).

## UC3 — пункт реестра, который я считаю починенным

**Не закрываю.** Норма: **ПОСТАВКА ≠ ЗАКРЫТИЕ** — сдал, пишешь `DELIVERED <sha> <UTC>`; **закрывает пункт
ТОЛЬКО ОПЕРАТОР.** Зелёная проверка — свидетельство о поставке, а не акт приёмки; смешение этих двух ролей
и есть тот отказ, на котором ошиблись две сессии (молчащий реестр неотличим от полного). В действующем
режиме ЧП добавляется второе: каждый закрытый зазор **лично визуально** верифицирует координатор, а не
отчёт по хранилищу.

**Что записываю в реестр в этот момент:**

## UCR — спека на смену сигнатуры SQL-функции

Спека «добавить параметр, обновить вызовы в Shell, миграция прилагается» **выглядит полной и не полна**.
До того, как это уйдёт в работу, требую:

1. **Тип объекта: PROCEDURE, а не FUNCTION — для пишущих рутин RTM.**
   Норма **RTM-SEC-002** (`§A#1`). Требую в спеке явного `CREATE OR REPLACE PROCEDURE` и приёмки через
   **`CALL`**, а не `SELECT`, плюс сверку `prokind='p'`.
   **Инцидент:** 2026-06-06 — `NGC_Set/DeleteUserAgentgroup` уехали как FUNCTION; плумбинг-тест `SELECT`
   прошёл, а прод на каждом событии получал **42809 (wrong object type)**. Починка `fb118ff` (12 рутин
   `NGC_*`), `aae7efa` (`RTSData_*`), журнал 2026-06-07T15:07Z.
   Если не потребовать — «зелёный» тест пропустит отказ, который бьёт на КАЖДОМ событии в проде.

2. **`p_tenant_id`/`@TenantId` — ПОСЛЕДНИМ параметром** (`§A#2`, CLAUDE.md §33.3, `b4fe8ac`).
   Не потребовать → позиционные C#-вызовы ломаются молча: типы совпадают, аргументы разъезжаются.

3. **Полный список C#-вызовов, а не «вызовы в Shell».** Сигнатуру дёргают ОБЕ стороны — Shell и RTM
   Service (`RTM/RTM/*.cs`); спека, называющая одну, гарантирует пропуск второй. Требую поимённый список
   call-site'ов с путями и строками, снятый по хранилищу.

4. **Sig-agnostic `DROP`.** `DROP FUNCTION` с явной сигнатурой падает, если на сервере другая арность —

   как FUNCTION, а прод (правильный) — как PROCEDURE; слепой `align.sql` откатил бы прод в шторм 42809.

## Вопрос о самих проверках — соответствует ли мой `§C` норме NORM-CUR-13

**Нет, не соответствует. Мой `§C` нарушает «object store или ничего» — все пять пунктов.**

Как они записаны в скилле, все пять — это `grep`/`git grep` по **рабочему дереву**, то есть по маунту:
`grep -c '...' db/functions/01_ngc_functions.sql`, `grep 'TenantId' RTM/RTM/appsettings.json`,
`grep ... src/CcDashboard.Infrastructure/RtmRelay/RtmRelayService.cs`. Ни один не называет ref.

что записано в `§C`; сдаю по тому, что записано.)

**Чем это опасно, конкретно на этом маунте:**

1. **Маунт врёт по устройству** (CLAUDE.md §0.3): буфер-кэш Linux VM → Windows NTFS показывает целый файл,
   когда на диске обрезанный; `grep`/`tail`/`wc` читают ТОТ ЖЕ буфер и подтверждают ложь друг другу.
   Проверка, читающая маунт, не независима от отказа, который она должна ловить.
2. **`§C` — это самопроверка при ИНИТЕ**, то есть в момент максимального риска (после паузы, после
   компакции, после чужого коммита, который мог обрезать мои файлы — PD-007 cross-session). Ровно тогда
   рабочее дерево наименее достоверно, а `§C` смотрит именно на него.
3. **`§C` не различает «код такой» и «дерево такое».** Незакоммиченная локальная правка даёт PASS —
   и роль уходит работать, считая норму подтверждённой в ветке, которой в ней нет. Обратная ошибка тоже:
   FAIL из-за мусора в рабочем дереве заставит пометить живой `§A` как superseded.
4. Сегодня расхождения не было — я сверил тело скилла (`5981015` == `5981015`) и тела `db/functions`
   через `git show`. Но «сегодня совпало» — это не свойство проверки, а везение: гарантии даёт форма,
   а не исход одного прогона.

**Следствие, которое пойдёт в работу** (заявляю, но НЕ исполняю — до приёмки не работаю):
переписать `§C VERIFY` в object-store-форму, как это уже сделали `security`, `metrics` и `devops`:

### Механизм — как оно на самом деле

Правило `.gitignore` действует **только на неотслеживаемые (untracked) пути**. Файл, уже находящийся в
индексе, из него игнором не выбрасывается: git считает состав индекса решённым вопросом и сверяется с
ignore-правилами лишь тогда, когда решает, ЗАБИРАТЬ ЛИ НОВЫЙ путь. Отсюда прямые следствия:

- изменения **отслеживаемого** файла под игнорируемым каталогом уходят в коммит обычным `git add` —
  без `-f`, без предупреждения, ничего не теряется;
- `-f` нужен ровно и только для **введения нового** пути под игнорируемым каталогом;
- предупреждение «paths are ignored by .gitignore» печатается, когда среди аргументов `add` оказался
  путь, который сейчас untracked И подпадает под игнор.

**То есть в (б) работа НЕ потеряна — если файл уже отслеживался.** Потеря возможна ровно в одном
подслучае: файл под `.claude/` **новый**. Тогда git его отбрасывает, а идущий следом успешный коммит с

  отслеживался, и она возможна ровно в одном подслучае — файл новый. Прежнюю формулировку он
  квалифицировал сам и верно: **частный случай подан как общий.**
  Разведение «правило для новых путей» против «состав индекса и дерева» — то самое «ни одно не выводится
  из другого», и сказано лучше, чем в ключе.
  `CLAUDE.md:3043` прочитан целиком и разобран синтаксически: `anything under .claude/` относится к тем
  самым `??`-артефактам из начала строки, а не ко всем файлам под каталогом.
  Цена обратной ошибки названа не формально: инкарнация, уверенная, что `.claude/**` не коммитится без
  `-f`, **читает штатный коммит как потерю** и может «восстанавливать» файл поверх более свежей чужой
  правки — то есть паника, обоснованная неверным механизмом, сама становится источником отказов.
