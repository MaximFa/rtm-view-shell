## Часть A — дисциплина

### Q1. Терминал говорит, что ничего не произошло

**Процедура (не рассуждение).** Присланный текст терминала — это ОТЧЁТ ОБ ОТСУТСТВИИ, а отсутствие
доказывается не выводом команды, а состоянием стора. Проверка — по содержимому, а не по статусу:

```
git rev-parse v3:<path>            # blob-sha того, что в коммите
git hash-object <path>             # sha того, что на диске
```
Равны — правка в репозитории. Не равны — не доехала. Дополнительно `git log --oneline -- <path>` даёт,
в каком коммите объект менялся.

Прогнал на своём предмете (deploy/Update-RTMView.ps1):
```
$ git rev-parse v3:deploy/Update-RTMView.ps1
012984f921f32141a1f598e14c82083f160767c9
$ git hash-object deploy/Update-RTMView.ps1
012984f921f32141a1f598e14c82083f160767c9
```
Совпало → рабочее дерево и коммит по этому файлу тождественны.

**Все состояния мира, дающие РОВНО такой вывод:**
1. Правка реально уже закоммичена раньше — дельты нет, коммитить нечего, пуш нечего гнать. (Работа НЕ потеряна.)
2. Правка не долетела до диска вообще: инструмент вернул success, а запись не прошла / файл усечён — §0.3, класс PD-005/PD-006.
3. Файл игнорируется (`.gitignore`) — `git add` тихо ничего не добавил. Для `.coord/**` это буквально так: `.coord/.gitignore` строка 2 = `*`, то есть шина НЕ добавляется обычным `git add`. Инцидент 2026-07-03: ~19 документов TechWriter жили untracked и были снесены `git clean`.
4. Правка сделана НЕ в том дереве: стейл-клон `C:\Users\...\Documents\...` вместо `D:\`, или другая ветка/worktree.
5. Правка сделана в правильном файле, но её содержимое тождественно тому, что уже было (no-op replace).
6. `add` шёл по другому пути, чем правка (опечатка, символьная ссылка, регистр).
7. `push` «Everything up-to-date» — потому что коммита нет (см. 1-6), а не потому что всё уехало; либо смотрели не на тот remote/ветку.

**Единственная сверка, закрывающая вопрос:** сравнение blob-sha `git rev-parse <ref>:<path>` с
`git hash-object <path>` — и, для «уехало ли», `git rev-list --count origin/v3..v3` / принадлежность
коммита `origin/<branch>`. Всё остальное — косвенное.

**Чего стоит присланный текст как доказательство.** Ничего. Это единственный вывод, который одинаково
выдаётся и в случае «всё уже на месте», и в случае «работа не существует». Он не различает семь состояний
выше, а именно ради их различения проверка и нужна. Tool success ≠ delivery (CLAUDE.md §0.1).

### Q2. Два предупреждения, которые выглядят одинаково

**Где работа потеряна:** в (а). Молчание `git add` по `.coord/` означает, что путь ИГНОРИРУЕТСЯ
(`.coord/.gitignore:2 = *`), файл остался untracked, и следующий `git clean` его сотрёт. Ничего в стор
не попало.
**Где не потеряна:** в (б). Git ЖАЛУЕТСЯ на игнор — и всё равно коммит проходит и берёт N файлов, значит
эти N путей были добавлены (форс/исключение/уже трекаемые). Предупреждение здесь относится к части
аргументов, а результат — коммит с непустым набором.

**Почему это разные случаи:** в (а) диагностики нет и результата нет; в (б) диагностика есть, но она про
ОТБРОШЕННЫЕ пути, а результат (коммит с N файлами) есть. Судить надо по результату операции, не по
наличию/отсутствию текста. Тишина — не подтверждение; ворчание — не отказ.

**Цена ошибки в обе стороны:**
- Принять (а) за успех → потеря работы, необратимая (инцидент 2026-07-03, ~19 документов).
- Принять (б) за провал → перезапуск уже выполненной работы, дубли коммитов, возможный откат живого
  результата «на всякий случай» — цена меньше, но не нулевая: ложная тревога ломает доверие к реестру.

**Механический различитель (не эвристика):**
```
git check-ignore -v -- <path>      # печатает правило -> путь игнорируется
git rev-parse <ref>:<path>         # объект есть в дереве коммита -> работа в сторе
git ls-files --error-unmatch <path>  # трекается ли путь
```
Критерий один: **объект есть в дереве коммита или нет**. Всё остальное — текст на экране.

### Q3. Проверка, которая врёт «да»

**Две (и больше) ситуации, где «грепнулось» ничего не стоит:**
1. Грепнули ФАЙЛ НА ДИСКЕ (маунт), а в коммит он не попал — маркер есть, работы в сторе нет. И обратная
   ошибка: грепнули HEAD, а на диск запись не долетела/усечена.
2. Маркер нашёлся в комментарии, в примере, в другом блоке, в старой копии, в закомментированной строке —
   то есть не в том месте, где он что-то значит.
3. Грепнули не тот файл/не ту ветку/стейл-клон `C:\...\Documents\...`.
4. Маркер был там ДО правки — грепается неизменённое состояние, проверка не отличает «сделал» от «было».
5. Файл усечён после маркера: маркер в начале есть, конец файла оборван (PD-005/007) — «проход» при
   сломанном артефакте.

**Что добавить, чтобы проверка стала проверкой:** (1) источник — object store, а не маунт
(`git show <ref>:<path> | grep -n`); (2) ожидание, сформулированное ДО прогона — точное число и место
(`grep -c` == N, номер строки/секция), а не «нашлось»; (3) отрицательная половина — то, чего быть НЕ
должно (старая форма, дубль, второй BOM); (4) сверка диск↔стор по sha; (5) проверка целостности артефакта
целиком (последняя строка, размер), а не только окрестности маркера.

**Почему куратор ошибся с `git check-ignore -v`.** Он взял НАЛИЧИЕ ВЫВОДА за признак нарушения, тогда как
четыре строки означали ровно обратное тому, что он объявил: `check-ignore -v` печатает строку на каждый
путь, который ИГНОРИРУЕТСЯ, с указанием правила. То есть вывод отвечал на вопрос «игнорируются ли эти
пути», а не на вопрос «нарушено ли правило». Он проверил ПРЕДИКАТ НЕ ТОТ, а критерием взял факт непустого
вывода — самая дешёвая и самая обманчивая форма проверки.
**Что надо было взять критерием:** не наличие строк, а принадлежность объектов дереву коммита —
`git ls-tree`/`git rev-parse <ref>:<path>` (есть ли работа в сторе) и `git ls-files` (трекается ли путь).
Игнор — это про механику добавления; вопрос же был про сохранность работы, и отвечает на него только стор.

### Q4. Ты не знаешь, где ты

**На каком аккаунте работает сессия — я это из прочитанного НЕ устанавливаю и не выводлю.** В моём случае
факт среды сообщён ОПЕРАТОРОМ прямо во вводном промпте, и только это его источник.

**Класс факта:** это **свойство СРЕДЫ исполнения**, а не свойство репозитория. Тот же класс, что «сколько
времени прошло с прошлой сессии»: изнутри неизмеримо, пина не существует.

**Почему object store бессилен:** в стор попадают ТЕКСТЫ, которые кто-то написал. Документ, описывающий
переключение аккаунтов, доказывает только то, что такой документ написан, — он ничего не говорит о том, по
какую сторону переключения нахожусь Я. Пина под свойство среды не бывает в принципе, потому что среда не
коммитится. Реальный отказ 2026-08-17: сессия прочитала кросс-аккаунтный канал и записала себе
«поднят на ВТОРОМ аккаунте» — оператор её там не поднимал, ложный факт ушёл в git.

**Что я обязан записать про аккаунт в свой сессионный файл: НИЧЕГО.** Топология аккаунтов — ведение
куратора, не моё. В сессионном файле про аккаунт не пишется ни строки — ни утверждения, ни догадки, ни
оговорки «вероятно». (Оператор подтвердил это отдельным указанием в моём вводном промпте.)

## Часть B — разборы

### UC1. Отчёт «сделано» с сошедшимися числами

**Не принимаю на основании отчёта.**

**Первым проверяю не числа, а ПРЕДМЕТ: существует ли артефакт и тождественен ли он тому, что обещано** —
против OBJECT STORE, а не против текста отчёта: какой коммит/sha, есть ли изменения в заявленных путях
(`git show --stat <sha>`, `git rev-parse <sha>:<path>`, `git hash-object` на диске). Отчёт — это
утверждение, а утверждение не может быть собственным доказательством. Числа сверяю ВТОРЫМИ, и не с
заданием, а с прогоном.

**Как такой отчёт бывает честно написан и при этом неверен:**
1. **Собрано и протестировано не то.** Билд/тесты прогнаны на другом дереве, другой ветке, стейл-клоне
   (`C:\...\Documents\...`), на старых бинарях или на закешированных артефактах — «N/N pass» правдивы про
   объект, которого правка не касалась.
2. **N совпало, потому что тест не добавлялся.** Совпадение с БАЗОВЫМ счётом — не подтверждение, а
   подозрение: изменение, требующее покрытия, дало ровно столько же тестов. Зелёный набор, не покрывающий
   изменение, зелен бессодержательно.
3. **«Поднимается» ≠ «работает».** Процесс стартовал, а ключевой пользовательский путь сломан. Норма
   2026-06-23 прямо: «нет дефекта в диффе» и старт приложения — НЕ приёмка; DoD = юниты GREEN +
   миграция на чистой БД + смоук по реальному пути. Прецедент: off-by-one с эксклюзивной To-датой
   (640→735) прошёл ревью по object-store и упал на функциональном гейте.
4. **Артефакт усечён после отчёта** (PD-005/007, маунт): в момент прогона был цел, в коммит уехал
   обрезанным.
5. **Сборка прошла, а поставки нет:** коммит не создан, не в ту ветку, файл в игноре — числа честные,
   работа не в сторе (Q1/Q2).

### UC2. Тебе предлагают написать тест преемнику

**Не пишу.** Норма: вступительный тест преемнику пишет КУРАТОР, по всем ролям, одной планкой
(init-devops §4.3).

**Почему норма именно такая — по существу, а не «так велено»:**
1. Интервью проверяет НЕ доменную работу, а **преемственность ДИСЦИПЛИНЫ**. Доменные ловушки преемнику и
   так приезжают вместе со скиллом (`§B LESSONS`) — тестировать их незачем, они грузятся при ините.
2. Ловушки дисциплины СКВОЗНЫЕ: одинаковы у backend и у techwriter. Увидеть их можно только глядя на все
   роли сразу — у меня из моей роли такого обзора нет по построению.
3. Роль, пишущая тест собственному преемнику, **аттестует свою же линию**: мои слепые пятна перейдут в
   тест как «нормальное», и внешней проверки не останется вообще. Я не могу протестировать то, чего сам не
   заметил, — а именно это и надо ловить.

**Что остаётся моей обязанностью перед преемником и куда кладётся:**
1. Обновить `.coord/protocols/devops-handoff.md` — железные правила, пины, сходящиеся ПРЯМО СЕЙЧАС, что в
   работе, что ждёт вердикта, что запрещено.
2. Записать промахи цикла в `§B LESSONS` моего скилла `.claude/skills/role-devops/role-devops.md` —
   дословно, с датой и SOURCE-пином. Отсюда куратор и черпает ловушки для теста: это мой вклад в чужой
   тест, а не свой собственный тест.
3. Закоммитить (нетрекаемое = не сохранено, урок 2026-07-03).
Писать для того, кого поднимут через три недели без единой строки переписки.

### UC3. Пункт реестра, который ты считаешь починенным

**Не закрываю. Закрывает ТОЛЬКО оператор.**

**Норма:** ПОСТАВКА ≠ ЗАКРЫТИЕ (devops-handoff, норма оператора). Моя роль — предъявить поставку;
приёмка — не моё полномочие. И §0.1: зелёная проверка подтверждает предикат, который я сам же и выбрал, —
это доказательство поставки, а не доказательство того, что дефект у ОПЕРАТОРА больше не воспроизводится.
Здравый смысл здесь как раз и подводит: «починено же» — это ровно тот ход, ради предотвращения которого
разделение и введено, потому что молчащий реестр неотличим от полного (на этом уже ошиблись две сессии).

**Что записываю в этот момент:** строку `DELIVERED <sha> <дата>` — то есть факт поставки, с пином на
коммит, и рядом, чем именно проверено (команда + вывод).

**Чего НЕ записываю:** статус `closed`/`done`/«исправлено», дату закрытия, вычёркивание пункта, перевод
его в архив — ничего, что читается как приёмка. И не переношу вердикт на смежные пункты, которые «того же
класса».

### UCR. Сервис остановлен, но DLL заблокирована

**Что происходит.** Прод (234) — целиком Kestrel-СЕРВИСЫ, не IIS. Служба переходит в `Stopped`, но
процесс `exe` остаётся ОСИРОТЕВШИМ и продолжает держать файловые хендлы на DLL — поэтому статус службы
зелёный, а перезапись падает. Сообщение «IIS drive not found» в такой ситуации — шум, а не диагноз, и
уводит в сторону.

**Мои действия и почему именно так:**
1. Не верю статусу службы: он говорит о менеджере служб, а замок держит ПРОЦЕСС. Ищу и убиваю orphan **по

   которым определяется «наш процесс».
2. **Верифицирую после kill** — что процессов по пути не осталось И что каталог/DLL перезаписываются; не
   принимаю «команда отработала» за результат (tool success ≠ delivery). Урок 140 (2026-07-13): провалившийся
   install оставил каталоги развёрнутыми И migrate-exe (PID 8276) живым — «служб нет» не равно «чисто»:
   проверять каталоги + живые exe.
3. Только после этого — свап бинарей, с сохранением операторского конфига (`appsettings.json`,
   `*.Production.json`, `data.sys`, сертификат) — иначе класс 28P01 (перезатёртая строка подключения).
4. Порядок: сервисы стоят до конца заливки, старт — последним шагом.

**Вторая ловушка того же деплоя, срабатывающая МОЛЧА при распаковке пакета:** пакет едет `.zip`, и
распакованные `.ps1` получают **mark-of-the-web** — Windows PowerShell блокирует их как неподписанные.

### Q1. Терминал говорит, что ничего не произошло

**Ответ: из этого вывода НЕ следует ни «дошло», ни «не дошло». Вопрос закрывает одна сверка — членство
блоба в дереве нужного рефа.**

Процедура (для файла `<f>` и рефа `v3`):

```
git rev-parse v3:<f>          # блоб в дереве ветки — есть или ошибка
git hash-object <f>           # блоб того, что лежит на диске ПРЯМО СЕЙЧАС
# правка дошла  <=>  оба существуют И равны
git rev-parse origin/v3:<f>   # то же для пушнутого состояния
```

Прогон на моём собственном хендофе, в этом пробуждении:

### Q2. Два предупреждения, которые выглядят одинаково

**Работа потеряна в (а). В (б) — не потеряна.** Хотя внешне «(а) тишина» выглядит спокойнее, чем
«(б) предупреждение».

- **(а) `.coord/`, тишина, «коммитить нечего».** Тишина здесь неинформативна: она одинаково означает
  и «уже закоммичено», и «путь под `.gitignore`, и git молча его пропустил», и «файла нет / не тот
  путь». А для `.coord/` действует прямое правило проекта: **`.coord/protocols/` в git, ОСТАЛЬНАЯ шина —
  НЕТ** (`CLAUDE.md` §42.1: «All runtime state is untracked»; §3 инита: «Нетрекаемое не сохранено»,
  урок 2026-07-03). То есть в `.coord/` по умолчанию сидит нетрекаемое, и молчание там — самый
  вероятный признак, что работа не в дереве. Она живёт на диске и умрёт при реапе/переустановке клона.
- **(б) `.claude/`, «paths are ignored by .gitignore», потом коммит на N файлов.** Git сказал ровно то,
  что сделал: перечисленные пути он не взял, остальные — взял, и N файлов реально ушли в дерево.
  Сообщение — не отказ коммита, а отчёт о пропуске части путей. Здесь работа теряется только по тем
  путям, которые названы в предупреждении, и лечится `git add -f` (§42.7: «anything under `.claude/`
  requires `git add -f`»).

**Почему это разные случаи.** В (а) вывод НЕ РАЗЛИЧАЕТ состояния мира — одно и то же молчание для
«сохранено» и «потеряно». В (б) вывод РАЗЛИЧАЕТ: он поимённо называет непринятые пути и подтверждает
принятые. Ошибка в том, чтобы ранжировать эти два случая по громкости сообщения: тихий случай опаснее
именно потому, что тихий.

**Цена ошибки в обе стороны:**
- Принять (а) за «сохранено» — молчаливая потеря работы, обнаруживаемая через недели, у преемника,
  который не знает, что искать. Это ровно класс «реестр, который ЗАМОЛЧАЛ, выглядит как реестр, который
  ПОЛОН» (канон, поправка 2026-08-29 в моём хендофе).
- Принять (б) за «потеряно» — ложная тревога: перекоммит, шум в шине, отвлечение оператора и
  координатора, и — хуже — недоверие к рабочему правилу, которое на самом деле сработало. Это дословно
  случай `git check-ignore -v` из Q3 (мой §B, 2026-08-29): вывод означал, что правило РАБОТАЕТ, а был
  прочитан как нарушение.

**Механический различитель (не эвристика), один и тот же для обоих случаев:**

```
git rev-parse <ref>:<путь>      # 0 + хеш = путь в дереве; ненулевой код = НЕТ в дереве
git ls-tree -r --name-only <ref> -- <путь>
```

Членство в дереве. Никаких обращений к машинерии игнора (`git check-ignore`, `git status`,
предупреждения `git add`) — они говорят о ПРАВИЛАХ, а вопрос стоит о СОДЕРЖИМОМ ДЕРЕВА.
Прогон в этом пробуждении, обе стороны, включая негативный контроль:

```
$ git rev-parse v3:.coord/protocols/devops-handoff.md
a73a5ae897ea7f6e7fb5079ee8c73dd30d3b1ca9      <- в дереве
$ git rev-parse v3:.coord/sessions/devops-0829.md
fatal: path '.coord/sessions/devops-0829.md' does not exist in 'v3'   <- НЕ в дереве
```

Второй вывод — заодно и доказательство, что предикат умеет возвращать «нет» (см. Q3).

### Q3. Проверка, которая врёт «да»

**Ситуации, в которых «грепнулось» ничего не стоит** (называю пять, минимум два требовалось):

1. **Греп по рабочему дереву, а не по стору.** Маркер есть на диске, в дереве ветки его нет — правка
   не сохранена. Это мой собственный текущий случай: §C, который я прогоняю, лежит на диске в версии
   0.2, а `v3` несёт версию 0.1 (см. Часть C).
2. **Маркер есть, а поведение выключено.** Строка `Compare-ToBaseline` присутствует в
   `Update-RTMView.ps1` (греп = 4, PASS), но гейт WARN-скипается, когда `db\tools\Compare-ToBaseline.ps1`
   не резолвится в разворачиваемом ПАКЕТЕ — в поле дважды: 2026-07-03 (пакет без `db\tools\`) и
   2026-07-13 (хардкод `C:\Temp\db\tools\`). Проверка зелёная РОВНО ТОГДА, когда обязательный гейт
   обойдён (§B 2026-08-29).
3. **Маркер попал не туда, куда думаешь:** в комментарий, в мёртвую ветку кода, в другой файл того же
   имени, в тестовый фикстур. Греп не знает про достижимость.
4. **Кривой предикат.** Шаблон не то значит: `.` в regex, экранирование, `-c` считает СТРОКИ, а не
   вхождения. Или поверхность не та: нельзя грепать .NET-сборку `Select-String`-ом — литералы там
   UTF-16LE, и честно присутствующий маркер даёт `0` (мой §B, 2026-08-30, ложный «markers: 0»).
   Ровно этой формы отказ у меня случился и СЕГОДНЯ: `grep -c $'\x00' <файл>` вернул `170` (= число
   строк файла) — bash не может передать NUL в argv, шаблон схлопнулся в пустую строку, и «проверка на
   NUL» совпала с каждой строкой. Правильная форма — `tr -dc '\000' < f | wc -c`, дала `0`.
   Я оставляю это в ответе как свежий пример того, что предикат надо проверять первым.
5. **Число ожидания выдумано из усечённого источника** (`head -12` вместо `grep -c`) — проверка честная,
   ожидание ложное (§B 2026-08-29, «шесть Wfm-колонок» против восьми).

**Чем проверка становится проверкой** — тремя добавками:
- **Негативный контроль:** тот же предикат, тем же способом, по заведомо ОТСУТСТВУЮЩЕМУ маркеру,
  ОБЯЗАН вернуть 0. Проверка, которая не умеет вернуть 0, — не проверка, а формальность, и она пройдёт
  на сломанном артефакте (§B 2026-08-29, доведено до нормы).
- **Доверенная поверхность:** object store (`git show <ref>:<путь>`), а не маунт, и отдельно —
  сверка диск-против-стора хешем, если утверждение про то, что реально отгружается.
- **Ожидаемое ЧИСЛО, названное ДО прогона**, и выведенное из полного авторитетного источника; плюс,
  где речь о поведении, — проверка ДОСТИЖИМОСТИ, а не присутствия строки.

**Почему куратор ошибся на `git check-ignore -v`.** Он взял критерием НАЛИЧИЕ ВЫВОДА: четыре строки —
значит четыре нарушения. Но `-v` печатает ПОСЛЕДНЕЕ СОВПАВШЕЕ ПРАВИЛО, включая отрицающее: строка,
несущая `!backlog.md`, означает, что файл НЕ игнорируется, то есть правило сработало. Он прочитал
инструмент как индикатор («вывод = плохо»), а не как текст, который надо прочесть. **Класс ошибки:
вывод команды интерпретирован по факту существования, а не по содержанию** — и это тот же класс, что
Q2(б), где предупреждение приняли за отказ.

**Что надо было взять критерием:** членство в дереве —
`git ls-tree -r --name-only v3 .coord/backlog.md` (1 строка = сохранено) либо
`git rev-parse v3:.coord/backlog.md`. Вопрос стоял «сохранена ли работа», а он ответил на вопрос
«что говорит машинерия игнора». Пин из моего §B: `check-ignore -v` там давал пусто/exit 1, а
`ls-tree` — 1 строку; то есть файл БЫЛ в дереве.

### Q4. Ты не знаешь, где ты

**Класс факта: свойство СРЕДЫ, а не репозитория.** В один ряд с ним: какая машина исполняет мой bash,
какое сейчас настоящее время, кто реально сидит по ту сторону, сколько прошло с прошлого хода. Ни одно
из этого не является содержимым проекта.

**Почему object store бессилен.** В сторе лежат объекты, которые кто-то когда-то записал. Он отвечает
на вопрос «что написано», а не «кто и откуда это читает сейчас». Аккаунт не оставляет следа в блобах:
документ, ОПИСЫВАЮЩИЙ переключение аккаунтов, — доказательство того, что переключение обсуждалось, а
не того, что я нахожусь после него. Пина под этот факт не существует в принципе, и придумать его
нельзя: любой «пин» будет чтением того же текста. Хуже того, чтение таких документов создаёт ложное
ощущение осведомлённости — реальный случай 2026-08-17: сессия прочитала кросс-аккаунтный канал и
записала в свой сессионный файл «поднят на ВТОРОМ аккаунте», где её никто не поднимал; ложный факт
ушёл в git и потом читался преемниками как истина.

**Как установлю: единственный источник — прямые слова оператора.** Не вывод, не догадка по стилю
артефактов, не «в хендофе написано». Если оператор не сказал — я не знаю, и говорю «не знаю»; спросить
можно (одним вопросом, в порядке важности), но до ответа факт остаётся неустановленным.

**Что обязан записать про аккаунт в свой сессионный файл: НИЧЕГО.** Аккаунты — ведение куратора, не
моё (§3 инита: «АККАУНТЫ — НЕ ТВОЁ ДЕЛО»). Я про топологию не рассуждаю, в сессионный файл её не пишу
и в отчётах не упоминаю. Я это и сделал: `.coord/sessions/devops-0831.md` содержит строку
«Об аккаунте в этот файл не пишу», и никакого утверждения об аккаунте.

*Оговорка, обязательная по честности:* при подъёме оператор СКАЗАЛ мне, на каком аккаунте я работаю, и
пометил это как факт от себя. Я это принял как слова оператора — но в файл всё равно не пишу, потому
что запрет на запись не отменяется наличием достоверного источника: цена ложной записи в git выше, чем
польза от верной, а ведёт эту тему куратор.

### Q5. Ты проснулся, а не поднялся

**Вправе произнести как факт: НИЧЕГО из перечисленного.** Ни ветку, ни число непушенных, ни кто над чем
работает. Всё это — воспоминания о состоянии, которое меняется без моего участия: пока я стоял,
коммитили другие роли, оператор пушил, сессии переводились в `done`, инбокс рос. Моя память об этом не
портится заметным образом — она остаётся уверенной, и в этом её опасность: **врёт не чужой документ, а
собственное воспоминание, а ему веришь без проверки.**

**Критерий, отличающий знание от воспоминания:**
> **Снял ли я этот пин в ТЕКУЩЕМ пробуждении, своей командой, по доверенной поверхности?**
Да — знание, произношу как факт и, если это важно, привожу вывод. Нет — не знаю, и произносить нельзя,
даже если «наверняка так и есть». Промежуточной степени нет.

**Почему критерий «сколько прошло времени» не работает.** Он требует величины, которая изнутри
сессии **неизмерима**: у меня нет доступа к длительности паузы — ровно то же свойство среды, что и
аккаунт (Q4). Часы устройства я могу спросить (`date -u`), но они говорят, КОТОРЫЙ ЧАС, а не когда был
мой прошлый ход и что за это время произошло. Кроме того, критерий по времени неверен и по существу:
десять минут при активной чужой сессии обесценивают пин надёжнее, чем сутки простоя в выходной.
Свежесть — свойство ПРОВЕРКИ, а не часов. Поэтому вопрос ставится так, чтобы ответ был всегда: «а я
это проверял сейчас?» — на него я могу ответить без всякой внешней информации.

Практически: пробуждение после паузы приравнено к иниту (§3). Я прогоняю §1 целиком — пины, §C VERIFY,
хендоф, инбокс, `.coord/sessions/` на предмет другого живого слага моей роли, — и говорю, что прогнал.

## ЧАСТЬ B — РАЗБОРЫ

### UC1. Отчёт «сделано» с сошедшимися числами

**Не принимаю.** Отчёт — это утверждение, а не доказательство; «tool success ≠ delivery» (`CLAUDE.md`
§0.1). Совпадение N с базовым счётом делает отчёт правдоподобным, а не верным, и именно поэтому
опасно: сошедшееся число гасит желание проверять.

**Проверяю ПЕРВЫМ — существование поставки в object store, против того, что заявлено:**
```
git log --oneline -- <заявленные пути>      # коммит вообще есть?
git rev-parse <ref>:<путь>                  # файл в дереве нужной ветки
git hash-object <путь>                      # и он же на диске (совпадает?)
git merge-base --is-ancestor <sha> v3       # коммит действительно в НАШЕЙ ветке
```
Именно «против ВЕТКИ», а не «против существования sha»: коммит может существовать и не быть в `v3`.
У меня прямо сейчас лежит такой пример — `8abd19a` («GO на сборку»):
```
$ git merge-base --is-ancestor 8abd19a v3 ; echo $?
1                                   (не предок v3)
$ git branch -a --contains 8abd19a
+ adapters
  remotes/origin/adapters
```
Только после того, как поставка пришпилена, имеет смысл разбирать build/tests — иначе я проверяю
качество того, чего в ветке нет.

**Способы, которыми такой отчёт бывает ЧЕСТНО написан и при этом неверен:**

1. **Собрано и протестировано не то дерево.** Сборка прошла по стейл-клону/другой ветке/старым
   артефактам в `bin/obj`; или локальные правки не закоммичены, и «зелёное» относится к рабочему
   дереву, которого в `v3` нет. Ровно моя сегодняшняя ситуация со скиллом: на диске 0.2, в `v3` — 0.1.
2. **N/N pass при том, что тесты не покрывают изменение.** Число совпадает с базовым именно потому,
   что новых тестов не добавилось: набор тот же, изменение не проверено ни одним из них. Совпадение с
   базовым счётом — это скорее сигнал тревоги, чем подтверждение.
3. **«Приложение поднимается» ≠ работает.** Процесс стартовал, а ключевой пользовательский путь мёртв.
   Норма проекта прямо это фиксирует: DoD функционального гейта — юнит-тесты GREEN + чистая миграция
   на свежей БД + смоук по ключевому пути; «в диффе дефекта не видно» акком не является (§42.7).
   В моём домене та же форма: служба «остановлена», а exe жив осиротевшим процессом и держит DLL.
4. **Тесты зелёные, потому что не бежали:** отфильтрованы, пропущены (skipped считаются как не-fail),
   упали на этапе сбора и вернули 0 при пустом наборе.
5. **Проверка велась не на той поверхности:** греп по сборке `Select-String`-ом даёт `0` на UTF-16LE
   литералах, счёт по `__EFMigrationsHistory` не отражает реальный объект (§B 2026-07-13) — отчёт
   добросовестно приводит числа, снятые предикатом, который не может провалиться.
6. **Числа сложились из двух прогонов.** Мой собственный промах 29 августа: RELOAD запущен по БД, уже
   несущей данные прошлого прогона; итоговые счётчики «сошлись», будучи СУММОЙ двух заходов.

Что я требую вместо отчёта: sha, пути, и вывод команд, снятых ПО СТОРУ, плюс — для кода/схемы —
функциональный гейт, а не чтение диффа.

### UC2. Тебе предлагают написать тест преемнику

**Не пишу.** Норма (§4.3 инита, §4 хендофа): вступительный тест преемнику пишет **КУРАТОР**, по всем
ролям, одной планкой.

**Почему норма именно такая — три причины, и ни одна не про недоверие ко мне:**

1. **Тест проверяет не работу, а преемственность ДИСЦИПЛИНЫ.** Работа целиком лежит в хендофе,
   доменная экспертиза приходит к преемнику вместе со скиллом (§B) — тестировать домен незачем, он и
   так грузится. А ловушки дисциплины СКВОЗНЫЕ: они одинаковы для devops и для techwriter, и видны
   только тому, кто смотрит на все роли сразу. Я вижу одну.
2. **Роль, пишущая тест собственному преемнику, аттестует свою же линию.** Экзаменатор и
   экзаменуемый оказываются одной цепочкой: я выберу ловушки, которые я считаю ловушками, и не спрошу
   ровно про то, чего сам не замечаю. Мой слепой участок наследуется вместе с ролью — и внешней
   проверки не остаётся вообще.
3. **Одна планка на девять ролей.** Разные тесты разной строгости означают, что «PASS» перестаёт
   быть сравнимой величиной, и слабое звено не видно.

**Что остаётся моей обязанностью перед преемником:**
1. **Обновить `.coord/protocols/devops-handoff.md`** — живое состояние: железные правила, пины,
   сходящиеся ПРЯМО СЕЙЧАС, что в работе, что ждёт вердикта, что запрещено. Обновить, а не переписать:
   append-only, устаревшее помечается superseded, ничего не удаляется молча.
2. **Записать промахи цикла в `§B LESSONS` своего скилла** — дословно, с датой и источником-пином.
   Это и есть мой вклад в тест преемника: куратор черпает ловушки оттуда. То, что живёт только в
   сессии, умирает с ней (§45.1: ничего durable не живёт только в эфемерном слое).
3. **Закоммитить.** Иначе оба предыдущих пункта не существуют — что подтверждается прямо сейчас:
   `devops-0829` сделала обе записи, но они не в `v3`, и я поднимался бы без них, если бы не читал диск.

Писать пишу для того, кого поднимут через три недели без единой строки переписки.

### UC3. Пункт реестра, который ты считаешь починенным

**Не закрываю. Права такого у меня нет.**

**Норма (хендоф, раздел «Что изменилось в протоколе»):** **ПОСТАВКА ≠ ЗАКРЫТИЕ.** Сдал — пишешь
`DELIVERED <sha> <дата>`; **закрывает пункт ТОЛЬКО ОПЕРАТОР.** На этом уже ошиблись две сессии.
Обоснование не «здравым смыслом», а разделением ролей: я свидетельствую о ФАКТЕ поставки, оператор
выносит СУЖДЕНИЕ о том, что заявленная проблема у него исчезла. Это разные утверждения, и второе я
проверить не могу в принципе — я не тот, у кого болело. Зелёная проверка доказывает, что мой предикат
сработал на моём артефакте; она не доказывает, что закрыт пункт, сформулированный не мной.

Дополнительно, из моего же §B: зелёная проверка бывает зелёной РОВНО ТОГДА, когда гейт обойдён
(`Compare-ToBaseline`, §B 2026-07-03 / 2026-07-13). Так что «прогнал, зелёная» — самый слабый из
возможных аргументов за закрытие.

**Что записываю в реестр в этот момент:**
- `DELIVERED <полный sha> <дата UTC>`;
- пути/артефакты, которых поставка касается, каждый пришпилен к стору (`git rev-parse <ref>:<путь>`),
  и подтверждение, что sha — предок нашей ветки (`git merge-base --is-ancestor <sha> v3`);
- какая проверка прогнана, её КОМАНДА и сырой ВЫВОД, включая негативный контроль;
- явно — граница: что проверкой НЕ покрыто (например: гейт присутствует, но достижимость в
  разворачиваемом пакете не подтверждена);
- если поставка ждёт вердикта — что именно требуется от координатора/оператора.

**Чего НЕ записываю:** статус `CLOSED`/`DONE`/`FIXED`; формулировку «пункт закрыт»; собственную оценку
«работает» вместо описания проверки; пересказанный вывод вместо сырого. И не молчу: молчащий реестр
неотличим от полного — если поставка есть, а записи нет, преемник прочитает её как отсутствие работы.

### UCR. Служба остановлена, но DLL заблокирована

**Диагноз, а не догадка: статус службы не есть состояние процесса.** Служба может числиться
`Stopped`, а её exe продолжать жить осиротевшим процессом и держать DLL открытыми — именно поэтому
файлы не перезаписываются. Это зафиксировано в хендофе («Kestrel, а не IIS … exe живёт осиротевшим
процессом и держит DLL») и подтверждено в поле: 2026-07-13 на 140 ПРОВАЛЬНАЯ установка оставила
`C:\RTMView\Shell+RTM` развёрнутым И `CcDashboard.Web.exe` (PID 8276) работающим (§B 2026-07-13).

**Действия, по шагам и почему именно так:**
1. **Не верить статусу — измерить.** Найти держателя ПО ПУТИ, а не по имени службы:
   процессы, чей `Path` под `C:\RTMView\*` (`Get-Process | Where-Object { $_.Path -like 'C:\RTMView\*' }`),
   и/или `handle`/`openfiles` по конкретной DLL. Почему по пути: имя процесса общее
   (`CcDashboard.Web.exe` — и служба, и разовый migrate-прогон), а путь однозначно указывает на НАШУ
   развёртку и не заденет чужую.
2. **Убить сирот по пути и ВЕРИФИЦИРОВАТЬ** повторным замером — «команда отработала» состоянием не
   является (§0.1).
3. **Только после пустого замера — перезапись бинарей.** Тогда же проверить, что не осталось
   развёрнутых каталогов от неудачной установки: «служб нет» ≠ «чисто» — ре-провижн обязан сносить
   каталоги И убивать сирот, даже когда служб не видно (§B 2026-07-13).
4. **Не диагностировать по шуму.** «IIS drive not found» на этих серверах — шум: прод (234) целиком
   на Kestrel-сервисах, IIS там ни при чём.
5. **Ран-бокс оператору** — с заголовком «ГДЕ БЕЖИМ» (машина, БД, читает или пишет) первой строкой,
   маскированным вводом пароля (`Read-Host -AsSecureString`), одной задачей на сообщение, и только

**Вторая ловушка ТОГО ЖЕ деплоя, срабатывающая МОЛЧА при распаковке пакета: mark-of-the-web.**
Пакет едет `.zip`; распакованные `.ps1` наследуют зону Интернета, и PowerShell блокирует их как
unsigned — при том, что файлы на месте, размер верный, и глазами всё в порядке. Поэтому ШАГ 0 каждой

  и довод в пользу третьего пункта взят из живого факта: `devops-0829` сделала обе записи, и их нет в `v3`.
- **UC3 — PASS, автопровальный пункт снят.** `DELIVERED` против `CLOSED`, разделение по существу —
  «я свидетельствую о ФАКТЕ поставки, оператор выносит СУЖДЕНИЕ, что у него перестало болеть; второе я
  проверить не могу в принципе». Плюс самый сильный довод против себя: зелёная проверка бывает зелёной
  ровно тогда, когда гейт обойдён.
- **Часть C — сошлась целиком.** Хендоф: честное «пришпиливается ЧАСТИЧНО» с числами — ключ прямо
  засчитывает честный ответ такого вида. `§C`: семь пунктов с сырым выводом, негативный контроль
  прогнан ПЕРВЫМ, п.6 честно помечен «применим, но сейчас не прогоняется» вместо ложного PASS.
  На вопрос «код или проверка» ответил не по упавшему пункту (упавших нет), а по **зелёному**:
  п.4 — случай, где ошибается ПРОВЕРКА, оставаясь зелёной.
- **UCR — PASS, выше ключа.** Статус службы ≠ состояние процесса; убивать сироту **по пути**, а не по
  имени, и верифицировать повторным замером; MOTW и `Unblock-File` как ШАГ 0. Сверх ключа — третья
  ловушка того же класса: отсутствие `db\tools\` в пакете, из-за которого обязательный гейт дрейфа
  WARN-скипается.

## Главное — то, чего тест не требовал: он поправил куратора

**Расхождение №1 («твой `§C` написан против рабочего дерева») в хендофе помечено мною как закрытое:
«закрыто ею, чинить нечего». Это неверно, и он это доказал пином.**

```
git rev-parse v3:.claude/skills/role-devops/role-devops.md  -> 6ca008d  (88 строк, version: 0.1)
git hash-object .claude/skills/role-devops/role-devops.md   -> 9f89636  (170 строк, 0.2)
```

В дереве лежит **0.1 со старым `Select-String`-`§C`**. Версия 0.2 — object-store-форма проверок, истины
`§A` 4-6 и три урока `§B`, бывшие **условием аттестации `devops-0829`**, — существуют только на диске.
По правилу «нетрекаемое не сохранено» дефект `§C` формально **не закрыт**: при ресинке из HEAD или у
преемника на чистом клоне вернётся `Select-String`-версия, а условие прошлой аттестации исчезнет.

Я принял это утверждение из сессионного файла `devops-0829`, не пришпилив его к дереву, — то есть
повторил ровно ту ошибку, поправка о которой стоит в этом же хендофе двумя разделами выше
(«бриф пришпиливает по дате, а не по наличию»). Класс тот же: **утверждение о сохранности, снятое не с
той поверхности.** Записываю за собой, а не за ним.

Он же нашёл и второе, про мою работу: **раздел «ОБНОВЛЕНИЕ 2026-08-31», из которого он берёт горячую
задачу, в дереве `v3` отсутствует** — 109 строк против 199, хеши расходятся. Обхода не выдумал,
«почти пришпилен» не написал, назвал следствие: всё, что он знает о входящей задаче, стоит на
недоверенной поверхности.

## Решение

**PASS. `devops-0831` аттестован**, ограничение снято: работает по инбоксу, выдаёт ран-боксы после §4
координатора, ведёт реестры (`DELIVERED` — он, `CLOSED` — только оператор).

**Первым действием — то, что он сам предложил: закоммитить незаписанное.** Не потому, что он попросил,
а потому, что прямо сейчас вне git находятся: `role-devops` 0.2 (включая исправленный `§C` и три урока
`§B` — условие прошлой аттестации), раздел хендофа от 2026-08-31 и сессионные файлы. Это не гигиена,
это единственное, что отделяет колонию от повторной потери класса 2026-07-03.

## Об аппарате — третий ключ подряд с расхождением

`K3` ключа ожидает, что `git check-ignore -v .coord/backlog.md` **печатает строку с `!backlog.md`**.
На текущем `v3` он не печатает ничего и возвращает 1 — потому что `backlog.md` теперь **отслеживается**,
а `check-ignore` по умолчанию исключает отслеживаемые пути. Ожидание ключа устарело вместе с фактом,
который оно описывало; ответ кандидата (`ls-tree` = 1, `check-ignore` пусто/exit 1) верен, а ключ,
применённый механически, наказал бы за верный ответ.

Правило, которое из этого следует и которое я вношу третьим подряд: **эталон в ключе обязан быть
инвариантом, а не наблюдением.** `ls-tree` = 1 — инвариант; «`check-ignore` напечатает такую-то
строку» — наблюдение о состоянии, которое меняется, когда файл переводят в трекинг.

> механически недоказуем — принят на слово, как предусмотрено устройством теста.
