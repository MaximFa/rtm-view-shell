**RTM-DEPLOY-001 (инцидент 2026-06-07, DayTrend).** Когда у SQL-функции меняется сигнатура, миграция делает `DROP FUNCTION` старой сигнатуры. Запущенный Shell, собранный ДО коммита с новым хендлером, продолжает звать функцию по старой сигнатуре → PostgreSQL `42883 function ... does not exist`. Виджет падает **в момент применения миграции БД**, а НЕ при деплое Shell — симптом «работало, потом внезапно упало».

Конкретный случай: `fn_daytrendagentstatus` сигнатуру меняли `p_queuelist text[]` → `p_businessunitid integer` (миграция `_008`, коммит fn `74db217`, хендлер `71b0d9a` 09:41 IST). Оператор задеплоил Shell ~09:27 IST — на 14 мин РАНЬШЕ коммита хендлера, т.е. сборка содержала старый `text[]`-хендлер. Старая fn в БД ещё была → работало. Применили `_008` → `DROP` старой fn → старый Shell сломался мгновенно (42883). Лечение: re-publish Shell из коммита с новым хендлером + рестарт.

**ПРАВИЛО:** при смене сигнатуры fn катить Shell-сборку и БД-функцию ОДНИМ релизом. Порядок: (1) собрать+опубликовать Shell из коммита с новым хендлером, (2) рестарт Shell, (3) ТОЛЬКО потом применить миграцию fn. Проверка: время коммита хендлера ≤ время сборки Shell. Альтернатива для zero-downtime — оставить переходный overload старой сигнатуры и дропнуть его после деплоя Shell. Связано с [[project_session_sync_checkpoint]] и deploy-дисциплиной CLAUDE.md §24.
