## Создание скиллов

Скиллы писать в `<папка-проекта>/<имя-скилла>/SKILL.md`, затем давать one-liner для копирования:
```powershell
Copy-Item "<проект>\<скилл>" "<проект>\.claude\skills\<скилл>" -Recurse -Force
```

**Why:** `.claude/skills/` write-protected в Cowork-сессии. Попытка писать туда — ошибка.

**How to apply:** Всегда использовать этот двухшаговый паттерн при создании любых скиллов.

## Формат ответа на «напиши одной командой»

Когда пользователь говорит «напиши одной командой» — дать только команду в блоке кода, без пояснений.

**Why:** Пользователь явно попросил краткий формат.

## Стиль технических скиллов

Скиллы должны содержать:
- Готовый код (не псевдокод) с реальными namespace'ами проекта (`CcDashboard.*`)

- Таблицу антипаттернов
- Pre-commit checklist

**Why:** Пользователь принял все скиллы в таком формате без замечаний — подтверждённый подход.

## Вопросы по коду — сразу готовить инструкцию для Claude Code

Когда пользователю или мне нужна информация из кода проекта (где определена сущность, кто пишет в таблицу, есть ли миграция, ссылается ли код на X, и т.д.) — **не описывать словами, что я бы сделал**, а **сразу выдавать copy-paste-ready промпт для Claude Code**, который пользователь скопирует в свою dev-среду.

Формат промпта:
- Контекст в 1-3 строчках (что за проект, какие соглашения именования и т.п.)
- Что проверить — нумерованным списком, с указанием конкретных папок и шаблонов поиска
- Ожидаемый формат ответа — структурированно (например, `# Origin`, `# Usage`, `# Verdict`, `# Recommendation`)
- Явная строка "не делай изменений в коде, только отчёт" (если речь про исследование)

**Why:** Claude Code писал весь код проекта — у него и есть полный контекст. Пользователь хочет переключаться между двумя средами: Cowork (со мной для архитектурных решений и документации) ↔ Claude Code (для самого кода). Описывать алгоритм исследования словами — потеря времени; готовый промпт пользователь копирует одним движением.

**How to apply:** Любой вопрос вида "где это используется?", "кто это создал?", "есть ли мигр​ация?", "ссылается ли код на X?" — ответ начинается с готового промпта в код-блоке, а не с описания шагов. Пояснения по интерпретации ответа Claude Code — после получения этого ответа.

## Все изменения в коде — только через Claude Code (CC)

**Правило:** Cowork-агент (я) **не вносит изменения в файлы проекта напрямую** — ни через Edit tool, ни через Python/bash в shell. Всё, что касается кода, делается так:

1. Я пишу детальную инструкцию для CC (готовый промпт)
2. Пользователь передаёт её в Claude Code
3. CC выполняет изменения, сборку, тесты и коммит
4. Пользователь возвращает результат мне — я обновляю документацию и PROJECT_STATUS.md

**Исключения (Cowork может делать сам):**
- Создание/обновление документации (`docs/`, `PROJECT_STATUS.md`, `MEMORY.md`, `widget-catalogue.md` и т.д.)
- Обновление `.gitignore`
- Git-операции с документами (коммит через index workaround)

**Why:** Договорённость с пользователем от 2026-05-26. Прямые правки файлов проекта через Cowork ненадёжны (mount-ограничения, Edit tool partial-write failures — PD-005). CC имеет полный контекст кода и работает в надёжной среде.

**How to apply:** Любая задача, которая требует изменения `.cs`, `.razor`, `.csproj`, `.json` файлов в `src/` или `tests/` — выдать готовый промпт для CC. Не писать код самому, не вносить изменения через shell.

## git push — только через cc_prompt_push.md, никогда напрямую из Cowork

**Правило:** Cowork-агент **никогда не делает `git push` напрямую**, даже через bash-инструмент. Пуш — исключительно через CC, по команде: `Выполни задачу из файла tools/cc_prompt_push.md`.

**Why:** Нарушение зафиксировано 2026-06-05 (RTM Prod Test3) — Cowork запустил `git push origin v2` напрямую. Правило явно закреплено в CLAUDE.md §37 и §0.7.

**How to apply:** Когда пользователь говорит «пушим» / «push» / «отправь» — выдать команду для CC, не запускать push самостоятельно.
