## 4. DBA CALL — how to apply the indexes on 140 (the migration defers this to me)
Use the **CONCURRENTLY** variant on 140: RTSData_Interaction is the hottest table (RTM upserts every interaction event); a plain CREATE INDEX takes a SHARE lock that blocks writes for the build duration and can stall ingestion. Run each statement standalone (autocommit, NOT inside a txn):
```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_rtsint_wfm_inq
  ON public."RTSData_Interaction" ("TenantId","InQueueDateTime")
  INCLUDE ("Workgroup","Direction","InteractionType","CallType","IsCallbackRequest");
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_rtsint_wfm_ans
  ON public."RTSData_Interaction" ("TenantId","AnsweredDateTime")
  INCLUDE ("Workgroup","Direction","InteractionType","CallType","IsAnswered","IsInQueue","TalkTime")
  WHERE "AnsweredDateTime" IS NOT NULL;
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_rtsus_wfm
  ON public."RTSData_UserStatus" ("TenantId","StatusGroup") INCLUDE ("UserId");
-- validity check (CONCURRENTLY can leave an INVALID index on failure -> DROP + retry):
SELECT c.relname, i.indisvalid FROM pg_class c JOIN pg_index i ON i.indexrelid=c.oid
WHERE c.relname IN ('ix_rtsint_wfm_inq','ix_rtsint_wfm_ans','ix_rtsus_wfm');
-- then the ledger row (the migration's self-record, run separately since CONCURRENTLY can't be in the txn):
INSERT INTO public.db_patch_history (migration_name)
VALUES ('20260721_001_wfm_indexes') ON CONFLICT (migration_name) DO NOTHING;
```
