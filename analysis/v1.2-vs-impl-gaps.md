## Data ownership model (added 2026-05-15)

Every entity/table referenced in this audit falls into one of five categories. The category
determines who owns migrations, who writes data, and what TZ v1.3 must describe (full
lifecycle vs. integration contract). The full taxonomy is to be formalized in **ADR-007**
(Database boundary). Cliff notes for this audit:

| Category | Conceptual owner | Migrations in prod | Shell writes? | Shell reads? | Examples |
|---|---|---|---|---|---|
| **1. Fully owned** | Shell | Our EF migration | Yes (our UI) | Yes | tenants, users, permission_groups, dashboards, dashboard_categories, tenant_settings, audit.audit_logs, pg_* junctions |
| **2. Backend — read-only** | Backend | Their system | No | Yes (reference for dropdowns) | *(reserved; no pure read-only entity currently)* |
| **3. Backend — proxy UI** | Backend | Their system | Yes (admin UI + **dual write to their API**) | Yes (dropdowns / dropdowns only — values are **transmitted**, not used by shell logic) | RTSGrid_Metric, NGC_BusinessUnit, NGC_Site, NGC_Supergroup, NGC_SupergroupAgentgroup, NGC_BusinessUnitQueueClassification, NGC_AgentGroups, NGC_Queues |
| **4. Backend — adaptation layer** | Backend | Their system | Yes (side-effect of widget create/edit/delete + **dual write to their API**) | GridId only | RTSGrid_* (Grid/Row/Column/Cell), RTSUserGrid_* (Grid/Column/ColumnsSet) |
| **5. Backend — endpoint** | Backend | n/a (no table on our side) | n/a | via SignalR Hub | `SubscribeToGrid` / `ReceiveGridData` events |

**Key facts:**
- **Production:** one shared PostgreSQL database `RTMViewDB` contains both shell and backend tables; two EF DbContexts (`__ef_migrations_history` + `__EFMigrationsHistory`).
- **Dev:** we emulate backend tables locally (our migrations create them), which is a technical debt — needs separate migration path or dev-only seeder for v1.3.
- **Dual write:** every change to category-3/4 tables must also notify backend via API (currently stubbed by `NoOpConfigurationApiHook`).
- **Naming convention:** shell tables — `snake_case`; backend tables — `PascalCase_With_Underscore`. In raw SQL, PascalCase names must be quoted.
- Reference: full taxonomy + antipatterns in `project_data_ownership.md` memory.

## Implementation status column

Every row has an Impl Status:

- `✅ Implemented` — fully working
- `⚠ Partial` — UI present but logic incomplete (e.g. screen renders but backend stub)
- `⏸ Deferred` — explicitly postponed to a later phase
- `❌ Not started` — neither UI nor backend exists

For each gap also identify:
- **Source of truth:** where the current state is documented (CLAUDE.md §, file path, screenshot name, commit)
- **ADR candidate:** Yes / No / Already in ADR-NNN — is this a decision worth an ADR?
- **Target v1.3 section:** which TZ section should incorporate this
